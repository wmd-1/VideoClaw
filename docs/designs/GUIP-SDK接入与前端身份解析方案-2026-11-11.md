## 0. 一页结论

| 维度 | 决定 |
|---|---|
| 目标 | `guip` 模式下按参考平台的同一套方式解析 GUIP 身份：加载真实 `GuipAPI.xc2.js`，从 `window.globalInfo()` / `window.promise.globalInfo()` 取 `userInfo.loginName`，纯内存保存，注入 `X-User-Login-Name`，无身份不挂载应用 |
| 模式边界 | **保留 `single`**：固定 `login=local`、忽略自报头、无头 200、`local` 视为管理员，不解析 SDK |
| SDK 来源 | **部署时由用户提供完整 `GuipAPI.xc2.js`**；仓库内只放同名占位文件，保证本地构建与无 SDK 环境不 404 |
| 加载方式 | `app/layout.tsx` 中用 `next/script` + `strategy="beforeInteractive"`，`src` 手动拼 `BASE_PATH` 前缀 |
| 身份来源优先级 | `?User=` / `?user=`（`allow_url_user !== false` 时） > `promise.globalInfo()`（1.5s 超时）> `globalInfo()`（要求 `userInfo` 非空）> 无身份阻断 |
| 身份存储 | 仅内存模块；移除 localStorage 身份缓存与"反代注入头兜底"（Q1，按用户指令采用建议） |
| 后端 | 不改：`/api/identity/mode` 保留用于模式判定，`/api/identity/me` 收窄为确认身份与取 `is_admin`，不再作为身份来源 |
| 部署 | 推荐覆盖宿主机 `.next-runtime/public/GuipAPI.xc2.js` 后 `docker compose restart frontend`；**不需要改 Dockerfile / Compose，不需要为本方案重建镜像** |
| 最大风险 | 前缀漏拼导致 SDK 404（全员身份缺失）；重新组装覆盖真实 SDK（Q7）；`beforeInteractive` 不阻塞 hydration，不能把"脚本已执行"当成"全局函数已就绪" |

## 2. 目标与非目标

### 目标

- G1：`guip` 部署下，页面加载即请求 `${BASE_PATH}/GuipAPI.xc2.js`，身份来自该 SDK 的全局函数。
- G2：身份解析顺序、超时与降级与参考平台 `authStore.ts` 一致；仅额外允许「脚本已加载但全局函数未就绪」时的有界短轮询（总预算 1.5s，见 §6.2）。
- G3：身份只存内存；刷新、重开标签页、换门户账号不会沿用旧身份。
- G4：无身份时不挂载业务应用，渲染 `IdentityMissing`，不降级为匿名或假身份。
- G5：`single` 模式行为不变。
- G6：API、SSE、媒体 URL 使用同一有效身份（沿用现有 `apiFetch` / `identityHeaders` / `getLoginName()` 收口）。

### 非目标

- N1：不建设用户表、密码、JWT、登录页；身份仍由上游 GUIP 提供。
- N2：不改后端身份中间件、`get_current_user`、归属校验、`trusted_proxy_cidrs`。
- N3：不改 `Dockerfile.frontend`、`docker-compose.yml`、构建脚本、依赖清单。
- N4：不处理参考平台的 WS query 通道（VideoClaw 无 WebSocket）、配额、收藏桶等无关机制。
- N5：不重新打开主方案 v18.1 已关闭的 §8.1 实施结论；本方案是**增量变更**，用于收口 SDK 加载与纯内存口径。
- N6：不在本方案中实施代码或修改 OpenSpec 工件。

## 3. 参考基准与"一模一样"的边界

### 3.1 参考基准

| 参考平台文件 | 契约 |
|---|---|
| `frontend/public/GuipAPI.xc2.js` | 同名 SDK 文件；仓库内为空占位，注释说明真实实现由 GUIP 平台注入 |
| `frontend/index.html:13` | `<script src="%BASE_URL%GuipAPI.xc2.js">`，在应用代码之前加载 |
| `frontend/src/store/authStore.ts` | `Window` 全局方法声明；`fetchGuipInfo()`：`promise.globalInfo()` 优先、1.5s 超时、`globalInfo()` 兜底；`initGuipUser()`：`?User=` > GUIP；身份纯内存；模块加载时清理历史 localStorage 身份键 |
| `frontend/src/main.tsx` | 先 `await initGuipUser()` 再挂载；无 `loginName` 渲染 `IdentityMissing` |
| `frontend/src/api/client.ts` | `beforeRequest` 注入 `X-User-Login-Name`，只放 ASCII `loginName` |
| Handoff §2.6 / §7 / 附录 A | 身份通道与失败语义（401 / 404 / 403）、无身份阻断 |

> 说明：参考平台的同名文件同样是占位，真实实现依赖门户运行时注入；VideoClaw 按 D4 由部署方提供完整文件，不依赖门户替换响应，二者不可混用。

### 3.2 框架差异：必须做的适配（不属于"不一样"）

| 参考平台（Vite） | VideoClaw（Next.js 16） |
|---|---|
| `index.html` 中 `%BASE_URL%GuipAPI.xc2.js`，构建期替换前缀 | `app/layout.tsx` 中 `next/script`，`src` **手动**拼 `${BASE_PATH}/GuipAPI.xc2.js`；`basePath` 不会改写手写 `src` |
| `main.tsx` 在 `createRoot` 前同步 `await initGuipUser()` | App Router 有 SSR，无法在挂载前同步 await；只能保证**业务组件在身份就绪前不渲染**，SSR 首帧为 Loading |
| Vite `base` 统一处理静态资源前缀 | Next `basePath` 由服务端剥离后匹配 `public/`；项目内 `BrandHeader.tsx` 的 `withBasePath('/jtyh.png')` 是同一机制 |
| 无模式概念 | 必须保留 `/api/identity/mode` 判定 single/guip，`/api/identity/me` 提供 `is_admin` |

### 3.3 VideoClaw 特有、不得删掉的能力

`GET /api/identity/mode`、`GET /api/identity/me`、SLB `basePath` 前缀 `/Bocom_Video_Generation`、媒体 `?user_login=` 通道、`apiFetch` 与 SSE 同源头注入、`single` 模式、`withBasePathUrl` 的媒体地址归一。

## 6. 方案设计

### 6.1 SDK 加载契约

| 项 | 契约 |
|---|---|
| 文件 | `frontend/public/GuipAPI.xc2.js`；仓库内为占位（空 IIFE + 注释"部署时由完整 SDK 覆盖"），真实 SDK 由部署方提供 |
| 对外 URL | `${BASE_PATH}/GuipAPI.xc2.js`，默认即 `/Bocom_Video_Generation/GuipAPI.xc2.js`；`NEXT_PUBLIC_BASE_PATH` 为空时为 `/GuipAPI.xc2.js` |
| 引入位置 | `app/layout.tsx`（RootLayout），使用 `next/script`，`strategy="beforeInteractive"` |
| 前缀来源 | 复用 `lib/basePath.ts` 的 `BASE_PATH`，或抽离为不含身份依赖的纯常量模块，避免在 server layout 中引入身份模块 |
| 加载语义 | 注入 `<head>`，在任何 Next.js 代码之前获取与执行；**不阻塞 hydration**；每次文档加载只执行一次，客户端导航不重复执行 |
| 禁止事项 | 不改名、不加 hash、不依赖门户改写 HTML；不使用 `onLoad` / `onError` 判断 SDK 就绪；不把"脚本已执行"等同于"`window.globalInfo` 已挂载" |

占位文件只用于本地构建、CI、无 SDK 环境与 single 部署不 404；它不提供任何身份能力，不能作为"接入完成"的证据。

### 6.2 `guip` 身份解析算法

引导入口仍为 `IdentityProvider.refresh()`，顺序如下：

1. `GET /api/identity/mode`（公开）。
2. `single`：`setResolvedIdentity("single", "local")`，直接完成，**不调用 `detectGuipLogin()`**。
3. `guip`：按优先级解析 login（`?User=` 仅在 `/mode.allow_url_user !== false` 时采纳；为 `false` 时跳过）：
   - `getUrlLogin()`（`?User=` / `?user=`）非空 → 采用；
   - 否则 `window.promise.globalInfo()`，1.5s 超时，取 `userInfo.loginName`；
   - 否则 `window.globalInfo()`，要求 `userInfo` 非空，取 `loginName`。
   > 解析逻辑需容忍「脚本已加载但全局函数尚未就绪」：在 1.5s 总预算内做短间隔重试（与 `promise.globalInfo()` 超时共用预算，不叠加），再判定无身份。
4. 解析结果为空 → `setResolvedIdentity("guip", "")`，渲染 `IdentityMissing`，**不挂载业务应用、不发业务请求**。
5. **先把解析到的 login 写入内存有效身份**（`setResolvedIdentity("guip", login)`），使 `identityHeaders()` 能注入头，然后再 `GET /api/identity/me`。
6. `/me` 成功：以其返回的 `login`、`is_admin` 固定本次有效身份与 UI 状态；此后不再被 URL 改写。若 `me.login` 与已解析 login 不一致（典型为反向代理改写/注入身份头），以 `me.login` 为准并记录 `console.warn`——API 归属以头为准，UI 必须与后端实际身份一致。
7. `/me` 失败（含后端 `safe_login` 拒绝非法登录名、`trusted_proxy_cidrs` 拒绝）：清空内存身份，进入身份缺失态，不回退 localStorage 或反代头兜底。

```ts
// 引导顺序示意（仅表达顺序，不是待提交代码）
const urlLogin = allowUrlUser ? getUrlLogin() : '';
const login = urlLogin || (await detectGuipLogin());
if (!login) return showIdentityMissing();
setResolvedIdentity("guip", login);   // 必须先于 /me，否则请求头为空
const me = await loadMe();            // 携带 X-User-Login-Name
setResolvedIdentity("guip", me.login);
```

### 6.3 纯内存身份模型与兼容导出

- `lib/identityState.ts`：`getLoginName()` 只读 `resolvedMode` / `resolvedLogin`（`single` 固定 `local`）；`setResolvedIdentity()` 只写内存；`getUrlLogin()` 仅供引导阶段使用，不再作为每次调用的回退来源。
- 删除 localStorage 身份读写：删除 `getStoredLogin` / `setStoredLogin`，并同步删除 `lib/identityGuard.tsx:12`、`lib/identity.tsx:14` 的 re-export；不保留空实现（避免后续误用）。`getLoginName()` 在身份未解析时返回空串，不回退 `?User=` 或存储。
- 启动时清理历史遗留键**仅限** `video-claw.login-name`（读取/删除均 try/catch）；`AppShell` 的 `SIDEBAR_OPEN_KEY`、`COMPLETED_TASK_DISMISS_KEY` 与身份无关，必须保留。
- 清理逻辑需有 `typeof window` 保护：`identityState.ts` 会经 `lib/basePath.ts` 被服务端引用。
- `components/IdentityMissing.tsx`："重试"改为 `location.reload()`，去掉 localStorage 清理；文案保留"请从 GUWP 门户重新进入本平台"。
- `components/AppShell.tsx`：**两种模式都移除「切换身份」按钮**（single 固定 `local`，无可切换身份）；`logout` 保留为内部兼容接口但不再由 UI 触发，并同步移除未使用的 `logout` 解构以避免 lint warning。
- `lib/basePath.ts` 不改逻辑：`currentLogin()` 继续读 `getLoginName()`，保证 API 头与媒体 `?user_login=` 同源。

### 6.4 `single` 边界

- `/mode` 返回 `single` → 固定 `local`，不解析 SDK、不读 `globalInfo`。
- 无身份头仍可 200；`apiFetch` 注入 `local` 或空头，后端均按 `local` 处理。
- 媒体 URL 仍追加 `?user_login=local`。
- 脚本常驻加载，但 **single 部署保留占位文件**（Q6），完整 SDK 只出现在 guip 部署的产物中，避免其在无门户环境产生副作用。
- 若某 single 部署误放了完整 SDK，需在验收中确认无强制跳转、无身份解析、无额外业务请求。

### 6.7 错误处理与降级

| 场景 | 行为 |
|---|---|
| SDK 404 / 加载失败 | 全局函数不存在 → 无身份 → `IdentityMissing`；不降级为匿名或假身份 |
| 脚本已加载但全局函数尚未就绪 | 在 1.5s 预算内短轮询；超时后按同步兜底与无身份处理 |
| `promise.globalInfo()` 超时 / 抛错 | 尝试同步 `globalInfo()`；仍失败按无身份 |
| SDK 返回空 `userInfo` | 不采纳，按无身份（与参考平台一致） |
| `/mode` 失败 | 保持身份校验中的错误态，不默认进入 single |
| `/mode` 返回 `allow_url_user=false` | 不采纳 `?User=`，改走 SDK；仍无身份则阻断 |
| `/me` 失败 | 清空内存身份并阻断，不回退缓存或反代头兜底 |
| `/me` 返回 login 与 SDK/`?User=` 不一致 | 以 `/me` 为准（后端实际看到的身份）并记录 warning；不阻断、不回退缓存 |
| `?User=` 显式身份 | 仅在 `allow_url_user !== false` 时允许并优先于 SDK；用户区显示"调试身份"角标（沿用主方案 §4.7） |

| 风险 | 影响 | 缓解 |
|---|---|---|
