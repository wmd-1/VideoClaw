## 3. R1 / P1：JSON 优先恢复使检查点事务保证失效

### 3.1 契约与完成声明

- [主方案 §6.3](用户与个人空间设计方案.md#L510-L530)：阶段完成先上传对象，再同事务写 stage/session/files；正常保存不再双写 JSON。
- [主方案 §17.6](用户与个人空间设计方案.md#L1184-L1187)：最后 completed payload 与当前执行状态分离，重跑失败后仍应恢复旧快照。
- [artifact-checkpointing](../../openspec/changes/user-space-isolation/specs/artifact-checkpointing/spec.md#L7-L52)：事务失败整体回滚，启动按 `version > 0` 恢复最后成功快照。
- [tasks 6.2、6.3](../../openspec/changes/user-space-isolation/tasks.md#L58-L59) 已勾选完成。

### 3.2 实现证据

1. [阶段完成路径](../../video-claw/video-claw/backend/core/orchestrator.py#L1347-L1351) 先执行 `save_session_to_disk`，再执行 `checkpoint_store.mirror_completed`。
2. [save_session_to_disk](../../video-claw/video-claw/backend/core/orchestrator.py#L1868-L1876) 实际写 JSON，并独立调用 `mirror_session`。
3. [启动装载顺序](../../video-claw/video-claw/backend/core/orchestrator.py#L1884-L1899) 先装 JSON，再装 DB；DB 装载跳过已经进入内存的 sid。
4. [JSON 装载](../../video-claw/video-claw/backend/core/orchestrator.py#L1969-L1971) 对 DB 检查点只做 `setdefault`，不会替换 JSON 中同名阶段。

因此，即使 repository 的 `complete` 内部事务正确，引擎整体仍存在事务之外的持久化与恢复来源。

### 3.3 待复验场景与影响

1. 阶段已有成功快照 A。
2. 重跑得到新结果 B，并先将 B 保存到 JSON。
3. 在阶段完成 DB 事务中注入失败，DB 正确保留 A。
4. 重启或重新装载该会话。
5. 当前装载逻辑会优先保留 JSON 中的 B，而不是以 DB 中的 A 为准。

影响不只是“多写了一份文件”，而是“最后一次成功提交”不再定义可恢复状态；会话状态与 stage/files 的原子性也不能仅靠后续事务证明。

### 3.4 修正建议

- 保留“DB 是权威源”的设计，不将正常 JSON 双写重新包装为合规过渡。
- 启动和懒加载统一读取 DB session 与 `list_checkpoints`；历史 JSON 只作为显式导入源或备份，不覆盖已存在的 DB 会话。
- 阶段完成涉及的 session 终态、stage payload/version、文件行只由完成事务提交，避免先独立提交完成状态。
- 普通进度保存与阶段完成保存区分职责：进度更新不能顺带覆盖最后成功快照。
- 失败后同步处理内存态，避免“DB 回滚但 API 仍暴露成功的新 payload”。这属于修复时必须检查的配套边界，本次未对所有内存分支逐一审计。

### 3.5 工件及关闭标准

- 重核任务 6.2、6.3；repository 已完成部分可以保留独立记录，但真实引擎接入不能继续混写为已完成。
- 增加“JSON 与 DB 同名阶段冲突”的启动、懒加载双入口测试。
- 验收：完成事务失败后重新构造引擎，恢复 A；stage version 不增加；不存在本次完成事务的半提交文件行。
- 验收：DB 已存在的会话不被备份 JSON 覆盖；恢复不批量下载对象。
- 验收：正常保存不更新历史 JSON；失败/中断状态仍可展示，但最后成功 payload 保留。

## 4. R2 / P1：新阶段产物未接通不可变 MinIO 对象链

### 4.1 契约与完成声明

- [主方案 §17.6](用户与个人空间设计方案.md#L1186-L1187)：每次执行有新 `execution_id`，对象键与 public_path 不复用；失败只清理本次对象。
- [数据库方案 §15](用户与个人空间-数据库方案.md#L599-L603)：local 只用于未迁移旧文件读取，不是新写入/部署模式。
- [OpenSpec design D4](../../openspec/changes/user-space-isolation/design.md#L47-L49)：重跑新建对象，DB 只切换检查点指针。
- [任务 5.1](../../openspec/changes/user-space-isolation/tasks.md#L49) 对适配器与同名重跑验证已勾选，但任务表缺少清晰独立的“真实阶段产物接入”闭环。

### 4.2 实现证据

- [文件登记逻辑](../../video-claw/video-claw/backend/core/checkpoint_store.py#L87-L101) 将产物写为 `storage_kind=local`、`bucket=None`、原 public_path。
- [阶段完成桥](../../video-claw/video-claw/backend/core/checkpoint_store.py#L114-L133) 将这些文件行直接交给 `StageArtifactRepo.complete`；该链没有执行不可变对象上传与 payload 路径切换。

不能由“MinIO 适配器具备 upload 方法”推导出“工作流的新产物已存入 MinIO”。本项证据针对阶段完成链，不据此泛化断言所有模块都没有上传行为。

### 4.3 待复验场景与影响

- 正常生成阶段产物，核查 DB 文件行和实际 MinIO 对象。
- 按方案只备份/恢复 PostgreSQL 与 MinIO，在不保留原本地结果文件的隔离环境读取媒体。
- 同名重跑并在 DB 提交前失败，再读取旧检查点媒体字节。

当前接入不能支撑“本地文件可重建”与“旧检查点对象不被覆盖”的保证。不能直接在生产环境删除本地文件来试验；复验应使用专用测试目录和对象前缀。

### 4.4 修正建议

建立真实阶段完成链：

```text
new execution_id
  --> stage output
  --> upload new objects
  --> build immutable public payload + file rows
  --> complete transaction
  --> expose committed payload
```

- execution_id 在本次执行中保持一致；同名重跑生成新 execution_id。
- 上传成功后生成带 execution_id 的 public_path，并同步替换待提交 payload 的相关路径。
- DB 事务失败只清理本次新对象，不删除旧检查点引用对象。
- 下游模型/ffmpeg 消费时物化到本地，DB/API 不持久化 `_refs` 缓存路径。
- 修复阶段链后，按既有契约复核任务/沙盒完成链的事务与存储接入，不以本项证据替代其独立验收。

### 4.5 工件及关闭标准

- 把适配器能力与阶段集成分成可独立验收的任务，关联 5.1、6.2、11.3。
- 新生成文件行应指向实际存在的 MinIO 对象；local 例外仅适用于历史兼容数据。
- 两次同名执行的 key/public_path 不同；第二次失败后第一次的对象内容校验值不变。
- 在隔离测试中移除本地缓存后，媒体读取/下游消费可由 MinIO 恢复。
- DB 失败不产生新检查点；清理失败被记录，且不影响旧对象。

## 5. R3 / P1：显式认领与重复导入会覆盖既有数据

### 5.1 契约与完成声明

- [主方案迁移段](用户与个人空间设计方案.md#L442-L456)：`--fallback-owner` 只填缺失；显式认领与普通导入区分；既有记录采用不覆盖语义，JSON 保留。
- [数据库方案 §10.1](用户与个人空间-数据库方案.md#L499-L504)：认领需显式指定、dry-run 与审计。
- [任务 3.7](../../openspec/changes/user-space-isolation/tasks.md#L27) 已勾选导入幂等与 owner 行为完成。

### 5.2 实现证据

- [CLI main](../../video-claw/video-claw/backend/db/legacy_import.py#L274-L290)：先 reassign，之后没有退出该操作，继续导入 sessions/tasks/sandbox。
- [会话导入](../../video-claw/video-claw/backend/db/legacy_import.py#L87-L105)：owner 取旧 JSON 值或 fallback，随后调用通用 upsert。
- [SessionRepo.upsert](../../video-claw/video-claw/backend/db/repositories/sessions.py#L27-L35)：冲突时更新 owner、status、current_stage、status_json、progress、meta 等字段。

### 5.3 待复验场景与影响

场景一：历史 JSON 的 owner 为 local，DB 中也存在该会话；执行 local→alice 认领。后续自动导入又把 JSON 的 local 写回，认领结果不能保持。

场景二：首次导入后用户更新会话，保留旧 JSON；重复执行普通导入。已有 DB 行被旧状态/旧元数据覆盖。

“总行数没有增加”只能证明没有重复插行，不能证明认领不回退或内容不被覆盖。迁移幂等必须同时包含数据内容与归属稳定性。

### 5.4 修正建议

- 认领与导入是独立模式：纯认领完成后不隐式运行 JSON 导入；混用参数应明确拒绝或另行设计可审计的顺序。
- 使用迁移专用的“仅不存在时插入”仓储入口。**不要直接把所有业务使用的 SessionRepo.upsert 改成不更新**，否则会破坏正常状态保存。
- 普通导入只补缺，不覆盖已有 owner、元数据或检查点；改变归属只能通过显式认领。
- 认领的 dry-run 输出源/目标 owner、资源类别及预计数量，执行日志记录结果；不记录密钥或不必要的个人内容。
- 同时核查 task/sandbox 的重复导入语义，防止仅修会话分支而保留同类问题。

### 5.5 工件及关闭标准

- 拆分 3.7 中的普通导入、显式认领、文件迁移验收；10.1 暂不放行。
- 旧 JSON 保留且内容未变时，认领执行后 owner 保持 alice，再次普通导入不能改回 local。
- 导入后更新 DB 再重复导入，owner、元数据、状态、checkpoint version/payload 均保持最新值。
- dry-run 前后 DB 和文件/对象内容均不发生变化；正式执行与预览的范围一致。
- 认领重复执行可解释、可审计，不产生无意的重新导入。

## 6. R4 / P1：Pipeline 事件流无法携带 guip 身份头

### 6.1 契约与完成声明

- [数据库方案 P13](用户与个人空间-数据库方案.md#L549-L552)：明确要求 Pipeline 事件流改 fetch，避免 EventSource 401。
- [OpenSpec design D1/D7](../../openspec/changes/user-space-isolation/design.md#L35-L37)：业务 API 使用 `X-User-Login-Name`；前端负责注入，不能把媒体 query 通道扩展为业务 API 身份回退。
- [任务 11.3](../../openspec/changes/user-space-isolation/tasks.md#L99) 已声明 P1—P20 验收完成。

### 6.2 实现证据

- [subscribePipelineTask](../../video-claw/video-claw/frontend/lib/workflowApi.ts#L383-L400) 仍创建原生 EventSource，没有走身份头注入链。
- [PipelinePage 调用点](../../video-claw/video-claw/frontend/components/pipelines/PipelinePage.tsx#L905-L913) 确实使用该订阅；出错后会更新前端 running 展示。
- [后端事件路由](../../video-claw/video-claw/backend/api/routers/pipelines.py#L386-L393) 依赖 `get_current_user` 并做归属校验。
- [guip 身份解析](../../video-claw/video-claw/backend/core/identity.py#L70-L78) 拒绝缺失身份。

### 6.3 触发条件与影响

在方案约定的“前端取得身份并注入请求头”部署中，普通 API 可以成功，但原生 EventSource 无法设置该自定义头，事件订阅返回 401。后端任务可能仍在运行，前端却收不到进度和完成事件。

若某部署另有可信网关为事件请求注入身份，表现可能不同；本次未核实实际代理配置。此例外不消除代码与 P13 的明确契约差异。

### 6.4 修正建议

- 采用 fetch＋ReadableStream，并复用现有 API 身份头构建逻辑。
- 保留既有 basePath、同源代理或已约定的流式地址规则，避免修身份时破坏 URL 寻址。
- 正确处理 SSE 事件跨 chunk、完整帧边界、非 2xx 响应与 JSON 解析错误。
- 使用 AbortController 清理订阅；切换任务/页面后旧流不得继续更新新任务状态。
- 401/404 与网络断开应保持可区分的失败反馈；取消订阅不能被当成模型任务失败。
- 不通过增加业务 query 身份回退、删除后端身份依赖或降级为全局 single 来规避问题。

### 6.5 工件及关闭标准

- 单列“Pipeline fetch SSE 身份接入”任务，关联 4.5、11.3/P13 与前端验收。
- guip 下本人订阅成功，缺身份 401，声明身份与任务 owner 不符 404。
- 前端真实订阅可收到 snapshot/progress/completed 或 failed 事件。
- SSE 分块边界变化不丢帧；切换任务和卸载后连接清理，无旧事件串写。
- 后端单独带头请求成功只能证明路由可用，不能替代前端订阅链验收。

## 7. R5 / P2：文件迁移参数未限制操作范围

### 7.1 契约与实现证据

- [object-store 旧文件导入](../../openspec/changes/user-space-isolation/specs/object-store/spec.md#L124-L131)：`--files` 只处理目标 owner，`--all-files` 需管理员二次确认。
- [CLI 参数与执行分支](../../video-claw/video-claw/backend/db/legacy_import.py#L263-L290)：两个参数只有不同 help 文案；最终共同传入全部 records，未筛 owner，也未实现二次确认。

### 7.2 触发场景与影响

历史目录同时包含 alice 与 bob。执行方案示例 `--fallback-owner alice --files`，期望只上传 alice 的文件；实际文件遍历包含 bob。

本项结论是**实际操作范围大于声明范围**，会增加非预期上传量、执行时长和迁移影响面；不是断言 bob 的文件被写入 alice 的对象前缀。

### 7.3 修正建议与需明确的决策

- 分别定义“缺失 owner 的填充值”和“本次文件上传的目标 owner”，不能仅凭参数名称默认两者永远等价。
- 为兼容现有方案示例，修订时应明确 `--fallback-owner alice --files` 的目标筛选规则；若增加独立目标参数，同步修改主方案、数据库方案、spec、CLI 示例和测试。
- `--files` 在进入文件遍历前过滤 records；`--all-files` 为显式全量分支，不与单 owner 范围静默混用。
- 管理员二次确认需要在方案里落成可执行协议：建议由受控运维入口授权，再配合明确的全量确认参数及审计。具体参数名须在修订时确定，本文不视为已经批准新增参数。
- dry-run 按 owner 展示候选/跳过/失败计数，正式执行沿用相同筛选逻辑。

### 7.4 关闭标准

- 双 owner fixture 下，单 owner 模式只上传目标文件，另一 owner 的 DB 行和对象均不变。
- 全量模式未满足确认条件时，在任何写入前拒绝；确认后处理范围与预览一致。
- 参数冲突明确报错，不能默认为全量。
- 重核 3.7；10.1、10.2 在范围验收完成前不得放行。

## 8. R6 / P2：已登记的 local 文件被永久跳过

### 8.1 契约与实现证据

- [数据库方案 §10.2](用户与个人空间-数据库方案.md#L506-L510)：旧文件上传 MinIO，未迁移的保持 local，校验失败保留 local。
- [当前文件导入](../../video-claw/video-claw/backend/db/legacy_import.py#L224-L228)：只要 public_path 已有行就跳过，不检查该行是否 local。

### 8.2 触发场景与影响

文件有合法本地内容，DB 已存在 `storage_kind=local` 行。执行文件迁移，无论重复多少次，都因“行已存在”而跳过；没有发生 local→minio 转换。

这与 R2 不重复：R2 是新产物生成链没接入 MinIO；R6 是既有 local 行的迁移路径缺失。修复其中之一不能自动关闭另一项。

### 8.3 修正建议

区分以下状态，不把“有 DB 行”直接当作“迁移完成”：

| 当前状态 | 建议行为 |
|---|---|
| 无文件行、有合法本地文件 | 上传、校验后建立 minio 行 |
| 已有 local 行、本地文件存在 | 上传、校验成功后更新原记录存储字段 |
| 已有 minio 行、对象校验正常 | 幂等跳过 |
| 已有 minio 行、对象不可确认 | 明确记录失败/待修复，不谎报已完成 |
| 本地文件缺失 | 记录缺失/跳过，不写入虚假的 minio 成功状态 |

- 上传和校验成功前不把记录改成 minio；失败保留原 local 信息及文件。
- 保持 public_path、父资源关系与 owner 一致，不通过另建冲突记录破坏唯一约束。
- 校验至少覆盖对象存在性与大小；是否增加内容哈希应结合成本确定，不能以无关对象存在替代本次上传成功。
- 日志区分新增、local 转换、已迁移跳过和失败，避免扫描数被当成成功迁移数。

### 8.4 关闭标准

- 同一 public_path 的 local 行迁移后变为 minio，bucket/key/size 可核验，不产生重复行。
- 再次执行为可解释的幂等跳过。
- 上传或校验失败后，local 记录和本地文件保持可用。
- 在专用测试环境不依赖原本地文件仍可读取同内容；正式数据不在验收时随意清理。
- 重核 3.7 的文件迁移实现，补齐 10.2 的转换验收。

## 9. R7 / P2：运行中删除的场景语义自相矛盾

### 9.1 冲突位置

[artifact-checkpointing spec](../../openspec/changes/user-space-isolation/specs/artifact-checkpointing/spec.md#L96-L113)：

- Requirement：运行中删除返回 409，本期不实现 cancel，防止 runner 写入已删除任务。
- Scenario：返回 409，但“runner 不再写入该任务”。

[任务 6.6](../../openspec/changes/user-space-isolation/tasks.md#L62) 的“删除不写回”也容易被理解为拒绝删除后停止正常写入。

### 9.2 问题及建议口径

拒绝删除表示没有删除成功。任务仍然存在且仍在运行，应继续正常持久化结果；要求停止写入等价于引入未经设计的取消/冻结语义。

建议将场景改为：

```markdown
#### Scenario: 删除运行中任务

- **WHEN** 用户删除 running 任务
- **THEN** 返回 409；任务及文件不删除，runner 继续正常执行并持久化结果
```

对 pending 任务采用同样的拒绝口径。把“不得写回已删除任务”留给允许删除的终态任务及相应竞态保护，不与 running 删除被拒绝混用。

### 9.3 实现与关闭标准

[当前后端删除分支](../../video-claw/video-claw/backend/api/routers/pipelines.py#L379-L382) 对 pending/running 返回 409，符合“不实现 cancel”的方向。本项不要求新增取消端点。

- 更新 spec 与任务验收措辞，使其含义一致。
- pending/running 删除返回 409，记录和文件保留；随后进度与最终结果仍能正常写入。
- 终态任务按既定规则删除；其他用户删除仍返回 404。
- 不应为了迎合错误场景而禁止运行任务的正常写入。
