# 迁移服务器迁移方案（无用户、旧工作流）

- 状态：**可执行草案**（2026-11-04）
- 适用：把当前 Docker 部署迁移到新的迁移服务器；源环境**没有真实用户账号**，历史工作流产生于 A/B/Q/C/D 优化之前，产物可能缺少 `prompt_source`、`resolved_fingerprint`、`asset_kind`、`evaluation` 等新字段。
- 目标：**原样保留旧数据、不在迁移中批量重写产物**；迁移后用只读默认值兼容旧数据，并在迁移环境完成优化计划中依赖真实模型/真实流量的验收。
- 配套：[工作流与 Prompts 优化计划](工作流与Prompts优化计划-2026-10-29.md)（迁移清单 9 项与已知边界）；[README](../../README.md)（部署与构建口径）。

## 一、迁移原则

1. **元数据以 PostgreSQL 为准（DB-only）**，媒体以 MinIO 为准；本地 `./data/code/result/` 只是运行时缓存，不能替代 DB/MinIO 备份。
2. **不批量迁移/回填旧产物字段**：缺 `asset_kind`、`prompt_source`、`resolved_fingerprint` 等由读取层按默认值处理，不写回、不批量重生图。
3. **不改写历史正文**：解析/提示词优化只影响新执行；旧 `description`、`rewritten_prompt`、版本记录保持原样。
4. **owner 语义保持一致**：源与目标的 `VC_USERS__MODE`、owner 值必须一致，否则旧会话在新环境“看不到”；无用户不等于可以随意改 owner。
5. **D4 hard 当前为 off**：迁移环境只有 warn 告警，没有上下文硬保护；不要配置 `VC_OBSERVABILITY_HARD_MODE`（尚未实现）。
6. **目标机只运行镜像，不在目标机重建基础镜像**；镜像用 `docker save`/`load` 搬运，前端运行时目录用已组装产物或按相同端口重建。

## 二、迁移前信息采集

在源服务器执行并归档。以下命令默认已载入 `.env`（`set -a; . ./.env; set +a`），变量值不要写进迁移记录：

```bash
cd <源部署目录>
git rev-parse HEAD
docker image inspect video-claw-backend:latest --format '{{.Id}} {{.RepoDigests}}'
docker image inspect video-claw-frontend:latest --format '{{.Id}} {{.RepoDigests}}'
umask 077
docker compose config > backup/compose.resolved.yml
chmod 600 backup/compose.resolved.yml
```

> `docker compose config` 会展开 `.env` 插值，可能包含 API Key、数据库密码、MinIO 密钥。`compose.resolved.yml`、`backup/env.backup`、`data/config/` 均按机密备份处理：仅迁移负责人可读、不入仓库、迁移完成后清理或存入受控密钥库；对外交接只用脱敏后的差异。

数据库与对象存储基线：

```bash
# 行数（至少记录 sessions / session_stage_artifacts / artifact_files / pipeline_tasks）
docker exec -i video-claw-postgres psql -U videoclaw -d videoclaw -c "
  select 'sessions' t, count(*) from sessions
  union all select 'session_stage_artifacts', count(*) from session_stage_artifacts
  union all select 'artifact_files', count(*) from artifact_files
  union all select 'pipeline_tasks', count(*) from pipeline_tasks;"

# 会话 owner 分布：决定目标 VC_USERS__MODE 是否要跟随
docker exec -i video-claw-postgres psql -U videoclaw -d videoclaw -c "
  select owner, count(*) from sessions group by owner order by 2 desc;"

# MinIO 桶与对象数
docker run --rm --network container:video-claw-minio \
  -e MC_HOST_src="http://${MINIO_ROOT_USER}:${MINIO_ROOT_PASSWORD}@localhost:9000" \
  minio/mc ls src/
docker run --rm --network container:video-claw-minio \
  -e MC_HOST_src="http://${MINIO_ROOT_USER}:${MINIO_ROOT_PASSWORD}@localhost:9000" \
  minio/mc du -h src/videoclaw src/videoclaw-saved
```

旧产物字段普查（用于确认兼容默认值覆盖范围）：

```bash
docker exec -i video-claw-postgres psql -U videoclaw -d videoclaw -c "
  select count(*) filter (where payload_json::text like '%prompt_source%') as with_prompt_source,
         count(*) filter (where payload_json::text like '%resolved_fingerprint%') as with_resolved_fp
  from session_stage_artifacts;"
```

同时记录：`.env` 中非密钥配置项、`./data/config/config.yaml`、`VC_USERS__MODE`、`VC_STORAGE__PUBLIC_ENDPOINT`、`BACKEND_PORT`/`FRONTEND_PORT`、当前测试基线（应为 **406 passed**）。

## 三、备份

> 备份目录必须放在仓库外（或至少加入 `.gitignore`），权限 `chmod 700`；不要把备份放进 `docs/`、`data/` 或任何会被提交/清理的目录。以下命令以 `backup/` 为例。

### 3.1 停写

先停止写入，避免 DB 与 MinIO 不一致：

```bash
docker compose stop frontend backend
```

`postgres`、`minio` 保持运行以便逻辑备份。

### 3.2 PostgreSQL

```bash
mkdir -p backup/minio backup/config
docker exec -t video-claw-postgres pg_dump -U videoclaw -d videoclaw -Fc -f /tmp/videoclaw.dump
docker cp video-claw-postgres:/tmp/videoclaw.dump backup/videoclaw.dump
docker exec -t video-claw-postgres pg_restore -l /tmp/videoclaw.dump > backup/videoclaw.list
```

### 3.3 MinIO

```bash
for bucket in videoclaw videoclaw-saved; do
  docker run --rm --network container:video-claw-minio \
    -v "$PWD/backup/minio:/backup" \
    -e MC_HOST_src="http://${MINIO_ROOT_USER}:${MINIO_ROOT_PASSWORD}@localhost:9000" \
    minio/mc mirror --overwrite src/$bucket /backup/$bucket
done
```

### 3.4 配置与镜像

```bash
cp .env backup/env.backup
chmod 600 backup/env.backup
cp -a data/config backup/config/
chmod -R go-rwx backup/config
docker save video-claw-backend:latest video-claw-frontend:latest | gzip > backup/images.tar.gz
```

`./data/code/result/` 可选备份（本地缓存/排障），不是恢复必需；如果旧产物仍依赖本地文件而非 MinIO，必须一起备份并在目标机保持相同路径。

### 3.5 备份校验

- `pg_restore -l` 无报错、表数量与基线一致；
- MinIO 每个桶的对象数与 `mc du` 总量与源一致；
- 任选一个旧会话，记录 `session_id`/`artifact` 数量，迁移后逐项对比；
- 备份目录不要放在 `./data/` 下，避免被后续清理脚本误删。

## 四、目标机准备

1. 安装 Docker 与 Compose；创建部署目录，目录结构与源一致（`docker-compose.yml`、`data/`、`video-claw/...`）。
2. **同步代码挂载路径**：compose 将后端源码逐项只读挂载到 `/app`（`api/`、`core/`、`db/`、`prompts/` 等），只搬镜像而不搬仓库会导致 `up` 失败或运行旧代码。目标机必须放入**与镜像匹配的仓库代码**，或显式调整 compose 去掉这些挂载；前端 `.next-runtime/` 同理，必须存在且匹配端口。
3. 导入镜像：`docker load < backup/images.tar.gz`；提前准备 `minio/mc` 镜像（源/目标机无外网时一并 `docker save`/`load`）。
4. 复制 `.env`、`data/config/config.yaml`；`backup/env.backup` 含密钥，权限设为 `chmod 600`，不要提交到仓库。按目标机修改端口、`VC_STORAGE__PUBLIC_ENDPOINT`（必须能被浏览器访问）。
5. **保持 MinIO 桶名与对象 key 不变**：`videoclaw`、`videoclaw-saved`；不要改 bucket 名，否则 DB 中 `public_path` 会失效。
6. 设置用户模式：
   - 源为 `VC_USERS__MODE=single` → 目标保持 `single`；
   - 源为 `guip` 且依赖上游代理 → 目标保留同一代理/信任配置；
   - 若源无用户、目标也无用户，**不要**为了“简化”把 guip 改成 single 后直接使用旧库：`sessions.owner` 是 NOT NULL，owner 不一致会导致旧会话列表为空。需要改模式时，先按 `db/legacy_import.py --reassign-from ... --to ...` 单独评估并备份。
7. 设置 4 个观测变量（与源一致，或按迁移环境调整）：

```env
VC_OBSERVABILITY_INPUT_WARN_CHARS=80000
VC_OBSERVABILITY_INPUT_HARD_CHARS=0
VC_OBSERVABILITY_EXECUTION_WARN_CHARS=300000
VC_OBSERVABILITY_EXECUTION_HARD_CHARS=0
# 不要设置 VC_OBSERVABILITY_HARD_MODE：尚未实现
```

8. 前端运行时：优先复制源机已组装的 `.next-runtime/`；若端口变化，必须在目标机按正确 `BACKEND_INTERNAL_URL`/`NEXT_PUBLIC_BACKEND_PORT` 重新构建，否则 API 会 500。

## 五、恢复步骤（按顺序）

### 5.1 只启动 DB 与 MinIO

```bash
docker compose up -d postgres minio
docker compose ps
```

### 5.2 恢复 PostgreSQL

先清空目标库（全新目标机才可执行；有数据必须先备份）：

```bash
docker exec -i video-claw-postgres psql -U videoclaw -d postgres -c \
  "DROP DATABASE IF EXISTS videoclaw WITH (FORCE); CREATE DATABASE videoclaw OWNER videoclaw;"
docker cp backup/videoclaw.dump video-claw-postgres:/tmp/videoclaw.dump
docker exec -i video-claw-postgres pg_restore -U videoclaw -d videoclaw \
  --no-owner --no-privileges /tmp/videoclaw.dump
```

### 5.3 恢复 MinIO

```bash
# 先建桶，避免 mc mirror 目标桶不存在
docker run --rm --network container:video-claw-minio \
  -e MC_HOST_dst="http://${MINIO_ROOT_USER}:${MINIO_ROOT_PASSWORD}@localhost:9000" \
  minio/mc mb --ignore-existing dst/videoclaw dst/videoclaw-saved

for bucket in videoclaw videoclaw-saved; do
  docker run --rm --network container:video-claw-minio \
    -v "$PWD/backup/minio:/backup" \
    -e MC_HOST_dst="http://${MINIO_ROOT_USER}:${MINIO_ROOT_PASSWORD}@localhost:9000" \
    minio/mc mirror --overwrite /backup/$bucket dst/$bucket
done
```

### 5.4 启动后端并应用新迁移

```bash
docker compose up -d backend
docker compose logs --tail=100 backend
docker exec -i video-claw-postgres psql -U videoclaw -d videoclaw -c \
  "select name from schema_migrations order by name;"
```

后端启动时会按 `db/migrations/*.sql` **自动补跑目标版本新增迁移**；已应用标记不会重复执行。若日志出现迁移失败，停止后端，保留现场，不要继续启动前端。

### 5.5 启动前端与冒烟

```bash
docker compose up -d frontend
curl -fsS "http://127.0.0.1:${BACKEND_PORT}/api/health"
curl -fsS "http://127.0.0.1:${BACKEND_PORT}/api/models" >/dev/null
```

浏览器打开首页 → 旧会话列表 → 任选一个旧会话打开 → 逐阶段查看产物/版本/参考图是否可读；预期旧数据可能显示“来源未知/未评估”，但**不得出现 500 或空白页**。

### 5.6 旧 JSON 会话（仅当源仍有 JSON 元数据）

当前部署已 DB-only，正常不需要。如果源目录 `data/code/data/sessions/*.json` 仍有未导入的历史会话，先 dry-run：

```bash
docker exec -i video-claw-backend /app/.venv/bin/python -m db.legacy_import \
  --fallback-owner <owner> --dry-run
```

确认数量、owner、ID 冲突后再去掉 `--dry-run`。**无用户环境**要明确 `<owner>` 用哪个值（通常与 `VC_USERS__MODE` 对应），不要用 `--reassign` 批量改 owner，除非单独评审。

## 六、旧工作流兼容：不迁移、只读默认

| 旧产物缺失/旧形态 | 迁移后行为 | 是否回填 |
|---|---|---|
| 无 `prompt_source` | 视频卡片“来源未知”；编辑框预填 `description` | 否 |
| 无 `submitted_prompt` | 有 `versions` 时显示“旧版本未记录提交正文（功能上线前生成）” | 否 |
| 无 `resolved_fingerprint`/`resolved_dimensions` | `needs_regeneration=true`；原因按 `prompt_source.stale_reasons` 回退，仍无则“无法定位具体变化” | 否 |
| 无 `manual_prompt` | 按 H3/description 自动来源，不显示“人工正文” | 否 |
| 无 `evaluation` | 角色/参考图显示“未评估” | 否 |
| `evaluation` 只有 `score` | 收敛为 `evaluated=null`/`unknown`，显示“未评估（旧记录）” | 否 |
| 无 `asset_kind` | characters 默认 `human`、settings 默认 `place`；不批量重分类/重生图 | 否 |
| 无 `meta.language` | 首次阶段执行前统一推断并写回；GET/status 不产生推断副作用 | 是（仅语言字段） |
| 旧 `selected`/版本 | 保持已存选中；不因重建 payload 改成 `versions[-1]` | 否 |
| 旧媒体路径 | 依赖 MinIO key/public path；迁移必须保持桶名与 key，否则图片/视频 404 | 否 |

**媒体路径的两种旧形态**：如果旧 `selected` 指向 MinIO public path，必须保持桶名与 key；如果指向 `/code/result/...` 或 `/app/code/result/...` 本地路径，必须把源 `data/code/result/` 一并迁移并在目标容器保持相同挂载路径，否则图片/视频 404。迁移前用旧会话抽样确认属于哪一种，不要假设全部已在 MinIO。

**不在迁移中做**：批量重生图、批量重分类 `asset_kind`、批量重算 `evaluation`、批量清空/重写 `versions`、把旧 `description` 当人工正文。

## 七、迁移环境验收

### 7.1 基础验收

```bash
# 测试套件（不要挂载 tests 到镜像；复制到容器再跑）
docker cp video-claw/video-claw/backend/tests video-claw-backend:/tmp/vc_tests
docker exec -i -e PYTHONPATH=/app -w /app video-claw-backend \
  /app/.venv/bin/python -m pytest /tmp/vc_tests -q
# 期望：406 passed（以目标版本实际基线为准）
```

- `GET /api/health`、`GET /api/models` 200；
- 旧会话可打开、可滚动、无 500；
- `schema_migrations` 含目标版本全部迁移；
- DB 行数、MinIO 对象数与迁移前基线一致；
- 任选旧片段：徽标/面板显示“来源未知/未评估”等默认值，不报错。

### 7.2 优化计划迁移清单（9 项，逐项执行）

1. **真实 H3 输出与 `<Picture N>` 编号**：用 I2VA/Ref2VA 真实跑一次 H3 + 视频；对比 `prompt_rewrite.items[].rewritten_prompt` 中的 `<Picture N>` 与视频请求的参考图顺序；期望编号与入参一致、无未定义标签。证据：prompt、视频请求摘要、截图。
2. **`submitted_prompt` 长度与折叠**：真实 H3 正文通常 >1000 字；打开视频详情，确认“本次已提交”240 字折叠、“展开全文”、`submitted_prompt_truncated` 时显示“仅记录前 1000 字”；刷新后仍保持。
3. **`resolved_dimensions` 原因**：生成视频后修改该片段时长（或参考图），触发重生成；期望“需重生成”显示具体原因（如“时长变化”），而不是“无法定位具体变化”。旧产物无 `resolved_dimensions` 时才允许“无法定位”。
4. **`needs_regeneration` 四组合**：分别构造/观察 manual fresh + 旧视频（true）、H3 fresh（false）、description stale（true + 原因）、未生成（versions 为空，UI 显示“未生成”而非“需重生成”）；四种组合截图/JSON 各一份。
5. **时长交集**：按真实模型能力验证 wan 2–15 / kling 3–15 → 有效 4–15 / 4–10；请求 2s、15s、20s，确认夹取/报错符合既定口径；记录 `duration_adjustment`。
6. **`17n+5` 帧对齐**：真实生成 5s/10s 视频，测量成片时长与目标偏差；已知 17n+5 帧对齐导致的偏差单独记录，不与时长交集混淆。
7. **A1 DB 回读**：真实提交一次角色/视频阶段后，用**新引擎实例**（绕过内存缓存）`get_state` 回读；逐字段对比 `selected`、`versions`、`description`、`evaluation`、`manual_prompt*`、`prompt_source`、`submitted_prompt`、`resolved_fingerprint`、`resolved_dimensions`；期望不丢字段。建议同时重启后端再读一次。
8. **旧产物评估徽标**：在真实旧数据上确认“未评估”与“未评估（旧记录）”区分正确；`score`-only 不显示为“已评估”；截图两张。
9. **观测变量与预算**：确认 4 个 `VC_OBSERVABILITY_*` 已生效；跑一段真实流量后执行 `tools/observability_report.py`，检查 P50/P95/Max、`over_warn`、执行总量 Top-N；`hard=0` 时 `over_hard=0`；`HARD_MODE` 未配置；根据 `input_chars` 分布再决定是否启用 A（fail），不要在迁移当天启用。

### 7.3 优化项与迁移动作对照

| 优化项 | 迁移时要做 | 验收 |
|---|---|---|
| A1 选优结果/DB 回读 | 不重写旧选中；真实阶段后回读 | 清单第 7 项；旧 `selected` 不被 `versions[-1]` 覆盖 |
| A1b 后台字段保护 | 不迁移字段；确认保护仍只作用于 `description`/`rewritten_prompt` | 后台单条重生成期间手改保留；`name`/`species` 不保护（已知边界） |
| A2 首帧/H3 上下文 | 旧产物保持原样；新执行才使用新上下文 | 首帧模式真实生成，画面/提示词无结构违规 |
| A3/Q9 评估落库 | 旧 `evaluation` 缺失只读“未评估”；不批量补 | 清单第 8 项；参考图与角色评估徽标一致 |
| B1 参考集顺序 | 保持旧产物；新执行按场景→角色有序列表 | 真实 Ref2VA `<Picture N>` 编号与顺序一致（清单第 1 项） |
| B2 人工正文/保护 | 旧 clips 无 `manual_prompt` 不伪造；新 PATCH 才写 | 保存人工正文后刷新仍在；`prompt_source=manual` |
| B3 邻接/完整上下文 | 旧产物不重算；新执行用完整有序分镜 | 单条重生成邻接正确（首/尾帧） |
| Q1 H3 权威正文 | 旧条目无指纹→unknown，不当作新鲜 | 清单第 1–3 项；H3 stale 回退 description |
| Q2/Q8 时长/选中 | 旧参数保持；新执行按交集与基线规则 | 清单第 5 项；执行期间手选不被覆盖 |
| C1 解析（旁白/英文场志） | 不重新导入旧剧本；新导入才使用新解析 | 新上传中英各一份，旁白/场志/角色清单正确 |
| C2 语言/资产类型 | 旧资产按容器默认（character→human，setting→place）；不批量改 | 旧资产可读；新资产五类固定样例选路正确 |
| C3 模板契约 | 目标版本模板随镜像/源码；不手工改旧产物 | 测试 406；真实请求无未定义占位符 |
| D1 观测 | 配置 4 个变量；确认 JSONL 可写 | 清单第 9 项；无正文/URL/密钥 |
| D2 grounding 缓存 | 进程内缓存不迁移；冷启动不命中但可重调 | 同图第二次执行命中；重启后重新调用不报错 |
| D3 分集/并行 | 旧剧本不重分集；新导入才走规则优先 | 标准/歧义剧本各一份；台词/情节并行顺序固定 |
| D4 预算 | 只配 warn；hard=0；不配 HARD_MODE | 报告有 P50/P95/Max；`over_hard=0`；真实分布后再决策 A |

### 7.4 已知边界（迁移时确认，不当作缺陷）

1. 后台保护与全量路径字段集不对称：`name`/`species` 不保护；
2. “payload 空值回退当前值”仅后台路径成立，全量路径空描述仍会覆盖已存；
3. 保护期间新改写不写 `versions`，模型新输出不保留；
4. H3 改写依赖视频模型配置，缺配置报 `Missing required model configuration`；
5. 旧评估仅含 `score` 收敛为 `evaluated=null`/`unknown`；
6. D4 hard=off：无上下文硬保护，超限由 provider 拒绝；
7. 首帧选优仍用模型自报分数，待真实模型对照。

## 八、回滚

触发条件（任一）：

- 后端迁移失败或健康检查连续失败；
- 旧会话大面积 500/空白，且 30 分钟内无法定位；
- MinIO 对象缺失导致旧媒体不可读，且无法从备份补齐。

步骤：

1. 停止目标前端/后端；
2. 保留目标 DB/MinIO 现场（不要 `down -v`）；
3. 恢复源机 DB/MinIO 备份到原机（或切换 DNS 回源机）；
4. 若目标已写入新数据，回滚会丢失这部分数据——迁移窗口内应禁止真实用户写入，或接受丢失；
5. 记录回滚原因、时间、涉及会话，更新迁移记录。

## 九、迁移窗口与检查表

建议顺序（无用户环境可缩短）：

1. T-1 天：备份、校验、目标机镜像/配置准备；
2. T0：停写 → DB dump → MinIO mirror → 目标恢复 → 启动后端迁移 → 前端冒烟；
3. T0+1h：清单第 1–9 项（真实模型项按可用性排期）；
4. T0+1 天：观测报告、旧会话抽查、回滚点确认。

最低检查表：

- [ ] 源 HEAD/镜像 ID/`.env`/config 已归档；
- [ ] PG dump 可 `pg_restore -l`，MinIO 对象数一致；
- [ ] 目标 `schema_migrations` 完整、后端健康；
- [ ] 旧会话可打开、旧媒体可读、无 500；
- [ ] 406 passed（或目标版本基线）；
- [ ] 迁移清单 9 项有证据；
- [ ] 4 个观测变量生效、hard=0、无 HARD_MODE；
- [ ] 回滚包与源机保持可用。

## 十、交付物

- 迁移记录（源/目标 HEAD、镜像 ID、迁移时间、执行人）；
- DB dump、MinIO 备份清单与校验结果；
- `compose.resolved.yml`、脱敏后的 `.env` 差异；
- 旧会话抽查截图/JSON、迁移清单 9 项证据；
- 观测报告（`input_chars` 分布、warn 计数、执行总量 Top-N）；
- 回滚演练记录（至少一次 dry-run）。
