## 分镜

### 【已完成】1.进度条一直是10%，但是文字会变化

现象：分镜面板内的进度条长期停在 10%，只有文案在换；收尾瞬间才跳到 95%→100%。

根因（已取证）：进度上报有两个不同口径的“进度源”。集内 4 条消息（处理中 / 已完成时长标注 / 已划分片段 / 正在检查连续性）上报时都不带百分比，被一个初始值为 10 的旧值原样复用，而最耗时的「逐片段设计」连消息都没有；唯一会推进的档位是“已完成集数”，而所有集并发启动、每集的片段又并发设计，各集完成时刻几乎挤在同一秒。现网会话 1793926098828 的单集分镜共 13 分 56 秒，其中“设计 16 个片段”2 分 07 秒、“连续性检查”10 分 01 秒，两段共占 87% 时长却全部报 10%。

已落地：分镜阶段改成按“模型调用步”计工作量的单一进度源（percent 只由它计算与发送，集数不再参与换算）。要点：

- 工作量按集登记为「1 次片段规划 + 片段数 + 1 次连续性检查」，percent = 10 + 85 × 已完成 / 总工作量，整数、只前进、运行期封顶 95，最后的 100 只在阶段完成时报。`done` / `total` 始终是真实调用步数，任何修正都不得改 `done`；未完成全部记账步时进度比封顶 0.999，所以 **95% 严格等价于“记账步全部跑完”**。
- 片段数初值用「标注 + 确定性打包」估算（与模型兜底路径同源、不调模型）；规划返回真实片段数后按差值**双向**修正：偏大当场收回分母（下限 `done + 1`），偏小放大分母并用「已挣得比例下限」防回落（宁可档位先停一会儿，也不虚报已完成步数）。
- 片段设计由“全部返完才知道”改为逐个返场即推进，文案形如「第 1 集分镜已设计完 7/16 个片段」；产物顺序仍按 segment_number，与改动前逐字一致。
- 长耗时调用（规划 / 等待片段 / 连续性检查）期间复用剧本修订那一份心跳（已提到智能体基类，两处共用同一实现与同一推进公式），每 8 秒渐近推进；量程只预支「下一步」的一半，最后一步未完成时不会提前显示 95%；量程耗尽后仍按节流间隔继续上报（消息附「已等待 X 分 Y 秒」），保证文字不断。多集并发时靠 4 秒节流窗约束事件量。
- 等待时长按步隔离（key = 集号+阶段）：并发多集时，一个集的里程碑不会把另一个集的“已等待”归零；每个片段返回后下一段从 0 起算。
- 连续性检查进入第 2 次尝试时补登记一次工作量并提示重试（重试的等待时长从 0 重算）。
- 口径边界：新增的片段级/心跳事件不携带清单预览与落库标记，持久化节奏不变（带 persist 的预览事件仍为 1 次开头 + 每集 1 次）；阶段名统一为「分镜设计」。改动面不限于分镜：心跳上抽动了 `base_agent.py` 与 `script_agent.py`，因此剧本修订阶段已纳入回归面。另立议题未动：连续性检查在模型读超时下两次共白烧 10 分钟的超时/重试预算（本轮只保证那段时间消息不断）。

已知边界（本轮不修，但不得当成已解决）：

1. **消息每 8 秒在动，进度数值在长调用期间会静止**。实测单集最长 584 秒、三集 600 秒 percent 不变。原因是模型接口没有 token 级回调，而又不收敛超时预算，按完成步加权就是物理上限；高百分比（90～92%）静止 10 分钟比低百分比更容易让人误判“快好了”，比原缺陷（卡在 10%）更接近真相但仍是已知体验边界。
2. **档位跳幅不封顶**。小 total 下「正常完成一步」天然就能前进 11～21 个百分点（实测 total=4、done 2→3 时 52→73），只封顶收缩不自洽；收缩（偏大修正）当场生效，极端组合下单事件跳 56 点、本轮复现用例跳 14 点。报出的是 `max(当前真实比例, 已挣得比例下限)`，不是平滑值。
3. **运行期间该阶段的 stale 标记在对外快照里不可见**。`_on_progress` 每次上报都会整体覆盖 `_overlays[session][stage]["progress"]`，`_view_dict` 又用覆盖层整体替换 `stage_progress[stage]`，因此阶段执行期间刚写入的 `stale_episodes` / `stale_reason` 不会出现在快照里。该遮蔽窗口 = 覆盖层存活时长（即阶段执行时长），**改动前后完全一致**；本次事件量从个位数升到 600 秒内 75～150 条，增加的是覆盖写入次数而非遮蔽时长（落库不受影响，收尾后以已提交视图为准）。
4. **估算准确度证据不可在 CI 回归**。它依赖本机历史会话库与 `tmp_verify/` 探针（取证：`probe_estimator_candidates.py`）；仓库内的 `test_segment_estimator_matches_deterministic_packing` 只锁“与确定性打包同源”这个实现口径（同义守卫），不是准确度断言。上一版的 `test_ledger_throttles_heartbeat_events` 把“心跳推不动数值”当成功能期望（T6b）、本版的数值停滞用例已显式标为已知边界，不再作为“已推平”的证据。
5. **分母修正与“不回退 / 不提前 95 / 不停滞”是不可能三角**（本轮采用 floor 方案后留下的具体代价，已量化）：
   - 放大分母后头几步就是原地不动。实测 K̂=2→真实 16：floor=0.25，**done=2/3/4 三步都仍报 31%**（真实比例已分别是 19/24/28%），直到 done=5 才重新前进（3/17 步停滞）；`test_growth_keeps_progress_moving_not_frozen` 把这个代价锁成断言。
   - 先放大再收缩、且收缩落点低于历史下界时，报出的档位会**高于**当前真实比例（报的是历史最高比例的下界）。实测：done=1 时先把 total 从 4 放大到 18（floor=0.25），再把分母收缩到 6，真实比例应为 **24%**，报出的是 **31%（高出 7 点）**；若收缩落点不低于历史下界（如收到 4）则不存在该偏差。`test_earned_floor_can_exceed_current_truth_ratio` 锁住这两个数。
   - 三者不可同时成立：分母变大时，既要 percent 不回退（得靠 floor 或改 done）、又要 95% 等价于真做完（得压住 floor）、又要每步都前进（得抬高 percent）——两两冲突。本实现选了前两个，并接受第三个代价。
6. **测试执行需容器内串行**。T12（`test_engine_level_progress_and_no_extra_persist`）走真实 `execute_stage` + 测试库写入，`tests/conftest.py` 的 autouse fixture 每个用例前 `TRUNCATE` 全部业务表；与另一个 agent 的 pytest 并发跑在同一 `videoclaw_test` 上会互锁（实测报 `DeadlockDetected` + `CommitParentMissing`）。无争用下连跑三次均 25 passed；失败不是进度逻辑缺陷，是多 agent 共用容器的串行约束。同理，取证探针在容器 `/tmp` 内同名会被并行 agent 的同名脚本覆盖（本轮实际遇到过一次），已改用唯一前缀：`probe_sb_r2_check.py` / `probe_sb_r3_floor_cost.py` / `probe_estimator_candidates.py`。
