# 剧本手改「一键智能更新」方案

- 日期：2026-11-18
- 状态：**设计提案，未实施**；实施前需转 OpenSpec 四工件（proposal / specs / design / tasks）
- 需求来源：用户在剧本页手改后，希望一次弹窗完成"人物场景解析 + 按需重跑下游"，范围交给模型/智能体判断，并让小白用户能理解、能上手
- 现行基线：归档变更 `openspec/changes/archive/2026-11-10-script-manual-edit-resync`（下称"上一轮"）。其口径是：**只同步与标记、不自动重跑**；下游重跑只有两个显式入口——剧本页「确认并继续」按阶段推进、以及「重跑第 N 集分镜」。本方案在不推翻"执行必须由用户显式触发"的前提下，把"逐个阶段点按钮"收敛为**一次计划确认**。

---

## 1. 现状与要解决的问题

| 现状 | 小白用户的体感 |
|---|---|
| 手改正文/角色后，系统只把下游标成"待确认"，参考图/视频上的提示是"该集分镜仍是旧内容" | 不知道"待确认"要自己点 |
| 要推动改动，需要依次在 剧本→角色→分镜→参考图→视频 各页点「确认并继续/继续生成」 | 5 次点击、5 个页面，且每次都要自己判断"这步要不要跑" |
| 「重跑第 N 集分镜」只重做分镜，不更新人物/场景清单，也不重出参考图/视频 | 以为点一下就能全好，结果下游还是旧图 |
| 人物/场景只在"导入剧本"时由模型抽取一次；手改正文不会重抽 | 新增了角色，角色阶段里根本没有它 |

目标：**保存后给一个"智能更新"弹窗**——系统给出"需要做什么、为什么、花多少"的清单，用户选"逐阶段确认"或"自动运行"，一次确认后把该跑的都跑完。

## 2. 目标与非目标

**目标**

1. 一次确认完成"重解析人物/场景 → 同步角色条目 → 重跑受影响集分镜 → 重跑受影响片段参考图/改写/视频 → 必要时重新合成"。
2. 范围由"确定性差异 + 模型裁决 + 硬守卫"三层决定，且**每个动作都给出人话理由**。
3. 提供两种推进方式：**逐阶段确认**（默认）与**自动运行**；选择可记忆。
4. 成本可见、可裁剪：弹窗里逐项勾选，显示"将调用哪些模型、重做多少集/片段/条目"。
5. 不破坏既有安全边界：不删任何图片/视频文件，不自动清空成片，不并发开第二条执行链。

**非目标（本轮不做）**

- 保存时静默自动执行（MUST NOT：执行仍必须由用户在弹窗里点确认）。
- 服务端后台断点续跑（页面关闭即中止；与现有执行链一致）。
- 跨会话批量重跑、A/B 双版本对比、按 token 计费账单级预算。
- 修改分镜阶段"该集已有 segments 即跳过"的消费语义（沿用上一轮）。

## 3. 用户流程（线框级文案）

### 3.1 保存后弹出"智能更新"弹窗

```
┌ 已保存。检测到 1 处改动需要更新下游 ──────────────────────┐
│ 你改了：第 1 集正文（新增 2 句台词、1 个新角色名「老张」）      │
│                                                          │
│ 建议执行（按顺序）：                                        │
│  ☑ ① 重新解析人物与场景   预计 1 次文本模型调用              │
│      理由：正文出现新名字「老张」，当前角色清单里没有          │
│  ☑ ② 更新角色阶段条目     新增「老张」1 项（需出图）          │
│  ☑ ③ 重跑第 1 集分镜      预计 1 次规划 + 约 5 次片段设计     │
│  ☐ ④ 重出受影响参考图     分镜跑完后按实际变化再确定（约 3 段） │
│  ☐ ⑤ 重跑受影响视频       会调用视频模型，费用最高             │
│  ☑ ⑥ 重新合成成片         本地合成，不调用模型                 │
│                                                          │
│ 推进方式：  ● 逐阶段确认（每一步停下来问你）                   │
│            ○ 自动运行（中途只在失败或需要你选择时停）           │
│            ☐ 以后都用这个方式                               │
│                                                          │
│ 说明：只会新增/更新，不会删除任何已生成的图片或视频。            │
│                              [ 暂不更新 ]  [ 开始执行 ]      │
└──────────────────────────────────────────────────────────┘
```

- 勾选默认值：①②③⑥ 默认勾选；④⑤ 默认**不勾**（费用最高，且 ④ 的目标要等 ③ 跑完才知道），但会显示预计数量，用户可主动勾。
- "暂不更新"= 保留上一轮的"标记 + 手动逐阶段"路径，不改变任何现状能力。

### 3.2 执行中

- 同一弹窗就地变成进度面板：`① 完成 → ② 进行中（2/3）→ …`，每步显示"完成/失败/跳过"与产物变化（新增 X 条目、替换 Y 个片段）。
- **逐阶段确认**：每完成一项停下，显示「本步结果摘要」+「继续下一步 / 跳过这一步 / 停止」；下一步若涉及模型调用会再次注明。
- **自动运行**：连续执行；仅在以下情况暂停并询问：模型不可用（409）、某一步失败、需要用户选择（如重抽出的角色与手改描述冲突、需要勾选删除条目）。
- 顶部横幅常驻「停止」；停止后已完成的部分保留。

### 3.3 完成后

摘要卡片：`新增角色 1、更新角色描述 0、重跑分镜 1 集（5 片段）、重出参考图 3、重跑视频 0、成片已更新`，并提示"未勾选的项目仍标为待确认，可稍后在对应阶段处理"。

## 4. 范围判定（本方案的核心）

三层，自下而上兜底：

### L1 确定性差异骨架（0 模型调用，立即返回）

沿用上一轮已有的判定与产物：

| 输入 | 用途 |
|---|---|
| `structure_fingerprint(before/after, scope=cast)` | 角色/场景集合或描述是否变化 |
| `structure_fingerprint(before/after, scope=body)` + `diff_episode_numbers` | 哪些集正文变了 |
| 各阶段 `status` 与产物存在性 | 哪些阶段"已经执行过"（决定要不要建议重跑） |
| `storyboard.episodes[].segments` / `reference.scenes[].episode` / `video.clips[].episode` | 变更集对应的片段集合 |
| `post_production.final_videos` | 是否建议重新合成 |

产出候选动作（见 §5 表），并给出每一步的"确定性理由"（例如"第 1 集正文变了"）。

### L2 模型裁决（1 次轻量调用，可关闭/可降级）

- 输入：`改前/改后正文差异摘要` + `现有角色/场景清单（名称+描述前 40 字）`；**不传全量剧本文本**（控制 token）。
- 输出严格 JSON（schema 校验，失败即降级为 L1）：
  ```json
  {
    "needs_cast_reparse": true,
    "reason": "正文出现新角色名「老张」且原清单没有",
    "cast_delta": {"add": ["老张"], "possibly_removed": [], "renamed": []},
    "storyboard_impact": "dialogue_and_cast",
    "notes": "第 1 集新增 2 段对话，镜头结构不变"
  }
  ```
  `storyboard_impact` ∈ `dialogue_only | dialogue_and_cast | structure_changed | unknown`。
- 用途：① 决定是否建议"重新解析人物与场景"；② 在 `dialogue_only` 时**不建议**重跑整集分镜以外的参考图/视频（台词换字通常不必重出图），在 `structure_changed` 时提高参考图/视频的推荐等级；③ 生成给用户看的一句话理由。
- 模型不可用/超时/输出非法：只保留 L1 候选，弹窗注明"未能智能判断，按确定性范围处理"。

### L3 硬守卫（0 模型调用，MUST）

- **动作白名单**：只允许 §5 表中的动作；模型输出里任何不在此表的项一律丢弃。
- **目标解析**：动作必须能落到具体 id（集号/片段 id/条目 id）；解析不到就降级为"提示，不执行"。
- **前置条件**：目标阶段无产物时不得执行该阶段（沿用"阶段 2 无产物不得创建"的既有边界）；已有 `selected`/`segments` 的条目在"重出图/重跑视频"动作里按"仅在受影响集合内"处理，不允许全量重刷。
- **成本阈值**（默认值，可配）：单次计划中「视频重跑片段数 > 10」或「图片重出 > 30」时，弹窗改为强制二次确认（红字列出数量）；未确认不得执行。
- **禁止项**：不删除任何磁盘文件；不自动清空 `final_videos`；不自动删除角色/场景条目（删除必须用户在剧本页显式发起）；不并发开第二条执行链（单会话单链，沿用 `_active_sessions`）。

## 5. 动作清单与执行器映射

> 原则：**不新造流水线**，全部复用已有执行器；本方案只新增"计划"与"重解析人物/场景"两件事。

| # | 动作 | 触发条件 | 目标范围 | 复用的执行器 | 成本量级 | 默认勾选 |
|---|---|---|---|---|---|---|
| ① | `reparse_cast` 重新解析人物与场景 | L2 判定需要，或用户手动勾选 | 全篇（新正文） | **新增**：复用导入时的 `import_meta_extract` 提示词，只产出 `characters`/`settings` 候选 + 合并策略（§7） | 1 次文本模型 | 勾（仅当 L2/规则判定需要） |
| ② | `sync_cast_items` 同步角色阶段条目 | ① 完成或用户手改了角色/场景 | 阶段 2 已存在产物 | 已有 `_rebuild_stage_items_from_script`（主键优先、同名保资产） | 0 | 勾 |
| ③ | `rerun_storyboard` 重跑分镜 | 有集正文变化 | 变更集 | 已有 storyboard `regenerate_episodes`（绕过 `ready_eps`，其他集不动） | 1 次规划 + 每片段 1 次设计 + 1 次站位检查/集 | 勾 |
| ④ | `rerun_reference` 重出参考图 | ③ 完成后有片段描述变化 | **延迟解析**：③ 实际变化的片段 id | 已有 `regenerate_scenes`（条目级后台重生成） | 每片段 1 次图生图 | 不勾（显示预计数） |
| ⑤ | `rerun_prompt_rewrite` 重跑改写 | H3 启用且 ④/③ 使条目失效 | 失效条目 id | 已有 `regenerate_items`/`revise_items` | 每条目 1 次文本模型 | 勾（仅在 H3 启用时出现） |
| ⑥ | `rerun_video` 重跑视频 | 参考图或描述变化涉及的片段 | 变更片段 id | 已有 `regenerate_clips` | 每片段 1 次视频模型（最贵） | 不勾（显示预计数） |
| ⑦ | `rerun_character_images` 新增角色/场景出图 | ② 产生新增条目 | 新增条目 id | 已有 `regenerate_characters`/`regenerate_settings` | 每条目 1 次图生图 | 勾（描述微调不默认勾） |
| ⑧ | `recompose_final` 重新合成成片 | 有成片且变更集属于成片集 | 受影响集 | 已有 post_production `regenerate_episodes` | 本地 ffmpeg，无模型调用 | 勾 |

**延迟目标解析（关键设计）**：④⑥ 的目标在计划生成时无法确定（要先跑完 ③ 才知道哪些片段变了）。计划里用表达式 `changed_segments_of(storyboard, episodes=[...])`，执行到该步时再解析。为此需要后端在分镜重跑收尾时记录**实际变化的片段**（新增 `stage_progress["storyboard"].changed_segments = {"1": ["seg_01_02"]}`，仅 UI 元数据、阶段执行时被覆盖清除），前端据此落到 ④⑥ 的 id。这是本方案唯一新增的后端"观测"字段。

## 6. 两种推进方式

| | 逐阶段确认（默认） | 自动运行 |
|---|---|---|
| 语义 | 每完成一项停下，用户点「继续下一步」 | 连续执行，直到完成/失败/需要选择 |
| 与现有「自动/手动」开关的关系 | 与"手动"一致：每步停 | 与"自动"一致：完成后自动 advance |
| 暂停条件 | 每步结束 | 预检 409、某步失败、需要用户选择（§7 冲突）、超出成本阈值 |
| 中途切换 | 任意暂停点可「切换为自动」；自动中随时可「停止」 | 同左 |
| 记忆 | 弹窗里勾"以后都用这个方式"→ 写入用户偏好；顶栏「自动/手动」仍可单独切换全局默认 | 同左 |

实现上沿用现有前端执行链（`handleConfirmStage`/`handleIntervene` 的"每步 SSE + 状态回写 + autoMode 自动 advance"），不新增服务端长驻链；区别只是**链的步骤来自计划**而不是固定的阶段顺序。

## 7. 人物/场景重解析的合并策略（防覆盖）

① 是唯一会"改剧本角色/场景集合"的模型动作，必须可预期：

1. **只增不删**：新清单里出现、旧清单没有的条目 → 追加（`pending`，需出图）；旧清单里没有在新清单出现的条目不自动删除，只在弹窗摘要里列出"正文未再出现：X、Y"，并提供勾选项"同时移除这些条目"（默认不勾）。
2. **同名不覆盖手改**：同名条目的描述若被用户手改过（`description_source=user` 或与旧解析值不同），MUST 保留用户版本，弹窗里列出"将保留你手改的描述：X"；模型给出的新描述写入 `suggested_description` 供用户比对（不自动生效）。
3. **改名按"删+增"处理并提示**：模型给出的 `renamed` 仅作为建议展示，不自动改主键（沿用上一轮"无主键首次改名不保资产"的已知限制说明）。
4. **主键口径不变**：新条目沿用 `script_revision.item_id()` 派生并回写剧本；阶段 2 重建仍走 `_rebuild_stage_items_from_script`。
5. ① 失败（模型不可用/输出非法）→ 该动作标记失败，后续 ②③ 仍可按"用户手改的角色集合"继续（不阻塞）。

## 8. 成本透明与"不会误删"承诺

- 弹窗逐项显示：**调用哪些模型**（文本/图生图/视频/本地合成）、**重做多少**（集数/片段数/条目数）、**预计顺序**。
- 未勾选的动作会注明"跳过；相关阶段仍保持『待确认』"。
- 常驻说明："只会新增或更新，不会删除任何已生成的图片或视频文件；成片只有在你勾选时才会重新合成。"
- 阈值触发时（§4-L3）红字二次确认；「自动运行」不得绕过阈值确认。

## 9. 失败、停止与恢复

| 场景 | 行为 |
|---|---|
| 预检 409（模型未配置/不可用） | 立即停在该动作之前，弹出既有"模型不可用兜底"（可上传替代或换模型），**不启动后续步骤** |
| 某步执行失败 | 自动运行也停；已完成动作保留并在摘要里标注；其余标记"未执行" |
| 用户点「停止」 | 同现有：断流 + `/stop`，已完成产物与条目不回滚 |
| 中途手改剧本 | 计划作废：前端检测到新的保存 → 关闭执行面板，提示"剧本又变了，请重新生成计划"（MUST NOT 用旧计划继续执行） |
| 页面关闭/刷新 | 链中止（与现有一致）；已完成部分已落库，刷新后按 `reconfirm`/`stale` 呈现未完成项 |
| 重复点击 | 单会话单链守卫（`chainRunningRef` + 后端 `_active_sessions`），第二次点击被拒 |

## 10. 接口与数据契约（草案）

只新增 1 个只读端点；执行复用现有端点。

```
POST /api/project/{sid}/resync-plan        # 只读：生成计划（不写产物、不启动执行）
  body: { "use_model_judgement": true }    # false = 只用 L1 确定性骨架
  200: {
    "plan_id": "<sha1(结构指纹+生成时间)>",
    "base_version": "<script structure fingerprint>",
    "change_summary": { "episodes": [1], "cast_changed": true, "body_changed": true },
    "actions": [
      { "id":"reparse_cast", "order":1, "title":"重新解析人物与场景",
        "targets": {"kind":"script"},
        "reason":"正文出现新角色名「老张」",
        "cost": {"text_calls":1},
        "default_checked": true, "guard": {"requires_artifact": null} },
      { "id":"rerun_reference", "order":4,
        "targets": {"kind":"changed_segments_of","episodes":[1]},
        "cost": {"image_calls_estimate": 3}, "default_checked": false }
    ],
    "warnings": ["视频重跑预计 5 个片段，将调用视频模型"],
    "model_judgement": {"used": true, "impact": "dialogue_and_cast"}
  }
  409: { "detail": {"code":"model_unavailable","stage":"script"} }
```

- **执行**：前端按 `actions` 顺序调用既有端点（`PATCH`/`intervene`/`continue`），`plan_id`+`base_version` 只用于**过期校验**（另一次保存后旧计划不得执行）。
- **执行结果的计划态**：每步结束后前端把该步标记为 `done/skipped/failed`，并调用 `resyncSessionView({refreshArtifacts:true})` 刷新（沿用 `stage-view-resync` 契约）。
- **新增观测字段**：`stage_progress["storyboard"].changed_segments`（分镜重跑收尾写入，供 ④⑥ 的延迟目标解析；阶段执行时被覆盖清除，不落产物）。

## 11. 与现有 `reconfirm` / `stale` 契约的关系（必须写进规格）

上一轮 `script-asset-sync` 的要求是"**不自动重跑任何阶段**"。本方案**不推翻**它，而是精确化：

- 保存剧本本身 MUST 仍然只做同步与标记（零执行）；
- 用户在"智能更新"弹窗里点「开始执行」= 显式动作，允许按计划**连续执行多个动作**（自动运行模式）；
- 计划未覆盖/未勾选的项仍保持 `reconfirm`/`stale` 提示；执行成功的动作清除对应阶段的 `reconfirm` 与过期详情；
- 成片仍只提示不失效，除非用户勾选 `recompose_final`。

因此规格变更属 **MODIFIED**（把"只允许单步显式动作"扩展为"允许一次确认后的多步计划执行"），不是新增旁路。

## 12. 验收矩阵（实施时必须逐条可测，零付费门内用假模型/夹具）

| 编号 | 断言 |
|---|---|
| A1 | 只改标题：弹窗不出现（或出现"无需更新"）；不产生任何动作 |
| A2 | 改正文 + 新增角色名：L1+L2 计划含 ①②③⑦，理由里出现新角色名；④在 ③ 完成后解析出正确片段集合 |
| A3 | 只替换台词：L2 判 `dialogue_only`，④⑥ 默认不勾；计划里不含 ①（无新名字时） |
| A4 | 手改描述后重解析同名角色：用户描述保留，弹窗列出"将保留你手改的描述"；模型新描述只进 `suggested_description` |
| A5 | 逐阶段确认：每步结束停下且状态正确；跳过某步后后续按依赖继续/终止（依赖未满足的动作标 `skipped`） |
| A6 | 自动运行：连续执行到完成；遇 409/失败即停，已完成步骤保留 |
| A7 | 成本阈值：视频片段数超阈值时不弹二次确认就点不动「开始执行」 |
| A8 | 过期计划：计划生成后再次保存剧本 → 旧计划执行被拒（409），提示重新生成 |
| A9 | 停止：执行中点停止，已完成产物不丢，未执行项仍为 `reconfirm` |
| A10 | 不删除承诺：任一路径下磁盘文件与 `final_videos` 数量不减（除非用户显式勾选 recompose 且成片替换） |
| A11 | 计划端点只读：调用前后产物与状态逐字节不变（除非触发重解析动作，而重解析不在计划阶段执行） |
| A12 | 历史兼容：点「暂不更新」后，行为与上一轮完全一致（标记 + 逐阶段 + 重跑本集分镜） |

## 13. 风险与替代方案

| 风险 | 缓解 |
|---|---|
| 模型判断不准，漏跑或多跑 | 三层判定（L1 定骨架、L2 只做增删建议、L3 守卫裁剪）；弹窗列出理由供用户改勾选；默认不勾最贵的 ④⑥ |
| 成本失控（小白点了自动运行） | 默认逐阶段 + 默认不勾视频 + 阈值二次确认 + 执行前显示预计调用数 |
| 重解析覆盖手改 | §7 合并策略（只增不删、同名保手改、改名仅建议） |
| 分镜跑完后目标集合变化导致计划与执行不一致 | 延迟目标解析 + `changed_segments` 观测字段；步骤间重新校验 `plan_id/base_version` |
| 与"自动/手动"顶栏开关语义混淆 | 弹窗的选项是"本次链路的推进方式"，并提供"以后都用这个方式"写入偏好；顶栏仍是全局默认 |

**替代方案对比**

1. **纯规则（不调模型判断）**：最省成本、可预测，但无法识别"正文新增了角色名"这类语义变化，用户仍需自己勾"重解析"。→ 作为 L1 骨架保留。
2. **纯模型规划（一次调用定全部）**：最"智能"，但不可解释、易过/欠执行，且模型失败即无计划。→ 被否。
3. **推荐：L1+L2+L3 混合**（本方案）。

## 14. 交付拆分与 OpenSpec 立项计划

建议拆成 2 个 change 依次实施（每个 change 完成后停下来等复审，沿用项目约定）：

1. **`script-resync-plan`**（核心）：计划端点（L1/L2/L3）、`changed_segments` 观测、人物/场景重解析动作与合并策略、**手改与 AI 修改共用的确认面板**（§16，必修而非可选）+ 两种模式的前端链路、验收 A1–A12。
   - 新能力：`script-resync-plan`（计划与范围判定）
   - MODIFIED：`script-asset-sync`（"只允许单步显式动作"→"允许一次确认后的多步计划"）、`stage-view-resync`（计划/执行面板的进度与错误呈现）
2. **`script-resync-polish`**（体验，可选）：偏好记忆、执行摘要卡片、成本阈值可配置、失败重试入口。

实施注意（沿用既有规则）：

- 后端测试全部在既有容器内执行，不新建/重建镜像；
- 零付费验收：重解析与分镜/图像/视频动作一律用假模型（monkeypatch）驱动，真实模型调用只在用户手动验收时发生；
- 每步完成即 `resyncSessionView({refreshArtifacts:true})`，避免回到"要刷新才正确"的旧问题。

## 16. 与现有「AI 修改」共用一套流程（统一变更流水线）

### 16.1 现状：AI 修改的完整链路

| 步 | 触发/位置 | 实际发生的事 |
|---|---|---|
| 1 | 剧本页「AI 修改剧本」卡片：输入修改方向 + 范围（全剧/单集） | `POST /intervene`，`action=revise_script`（`instruction`/`scope`/`episode_number`） |
| 2 | `script_agent._run_revise_script` | **一次 LLM 调用**产出 `episodes`（全剧或只目标集）+ `characters` + `settings`；`ensure_item_ids` 补主键（不就地改 `current`，保住 `base_version`）；算 `diff_episode_numbers`、`stale_storyboards`（已有分镜且正文变了的集）、`removed_items`/`user_edited_items`（对比阶段 2 得到"将被删除/被覆盖"的条目与资产数）、`base_version`（修订前内容指纹） |
| 3 | 返回 `requires_intervention: true` | 预览只写**预览层** `pending_revision`，正式产物与阶段状态不变 |
| 4 | 前端剧本页预览面板 | 显示摘要、逐集变更、将删除条目（含已有资产数）、将被覆盖的手改描述、过期集提示；按钮：应用修改 / 取消 / 重新输入 |
| 5 | 「应用修改」→ `action=apply_revision`（带 `confirm_removals`/`confirm_overwrites`） | 后端 `_run_apply_revision`：校验 `base_version`（正文又变了就拒绝）、校验未选中集逐字未变、按确认标志放行删除/覆盖、写 `revision_history`、清派生标注；返回 `revision_applied: true` |
| 6 | `_finish_stage` 收尾 | 与手改**同一条** `_sync_script_structure(before, baseline)`：阶段 2 条目重建（主键优先、同名保资产）→ 状态重算 → 剧本之后、后期之前的已执行阶段标 `reconfirm` → 有成片只写 `stale` → `current_stage` 归位剧本（无 running 时） |
| 7 | 前端介入链收尾 | 重取剧本产物、状态表回写所有阶段；当 `status_map.storyboard == "reconfirm"` 时再取一次只读快照刷新下游产物 |
| 8 | 之后 | 仍需用户点「确认并继续」或逐阶段「继续生成」才会真正重跑——与手改完全一致 |

### 16.2 两条入口的差异（现状）

| 维度 | 手工修改 | AI 修改 |
|---|---|---|
| 入口 | 剧本页直接改（PATCH） | 输入修改方向 → 模型改写 |
| 是否先预览 | 否（所见即所得） | 是（`pending_revision`，可取消/重新输入） |
| 危险项确认 | 删除条目时逐次 `window.confirm` | 一个确认框列出全部删除/覆盖项 |
| 变更信息来源 | 前端提交的 diff（后端按结构指纹重算） | 模型输出 + `diff_episode_numbers`/`removed_items`/`user_edited_items` |
| 落地后收尾 | `_sync_script_structure` | `_sync_script_structure`（**已共用**） |
| 下游执行 | 只标记，需逐阶段点 | 只标记，需逐阶段点（**完全一样**） |

**结论**：落地之后两条路已经是同一条收尾，差异只在"变更怎么产生、要不要预览"。所以"用一套流程"不是重构，而是把**入口之后的公共段**抽出来复用。

### 16.3 统一后的流程（建议作为实施口径）

```
入口 A：手工修改 ── 直接落地 ─┐
                              ├─→ 统一的「变更描述」─→ 统一的「更新计划」─→ 用户确认（含危险项+勾选+模式）─→ 执行链
入口 B：AI 修改 ── 预览+应用 ─┘
```

- **统一的变更描述**：`{ changed_episodes, cast_changed, removed_items, user_edited_items, stale_storyboards, base_version }`。手改路径由 `resync-plan` 端点算（L1），AI 修改路径**直接复用 `pending_revision`**（这些字段已经在预览里），无需再调模型做 L2 裁决。
- **统一的计划结构**：§10 的 `actions[]` 同一份 schema，两条路径共用 L3 守卫（白名单/前置条件/成本阈值/禁止项）。
- **统一的确认面板**：把现在的"应用修订确认框（删除/覆盖）"与新的"智能更新弹窗"合并为一个面板：
  ```
  ☑ 应用这次修改（将删除 2 项、覆盖 1 项手改描述）
  ☑ 更新角色阶段条目（新增 1）
  ☑ 重跑第 1 集分镜
  ☐ 重出受影响参考图（约 3 段）
  ☐ 重跑受影响视频
  ☑ 重新合成成片
  推进方式：●逐阶段确认  ○自动运行
  ```
  即：**AI 修改的"应用修改"不再是终点，而是这个面板的第一项**；`confirm_removals`/`confirm_overwrites` 变成面板里的危险项勾选，后端仍做强校验（不勾不放行）。
- **统一的执行链**：两条路径都按计划顺序调用既有端点（§5 表），逐阶段/自动只差"是否自动 advance"。
- **AI 修改路径的差异化默认值**：修订模型已经重写过 `characters`/`settings`，所以「重新解析人物与场景」在该路径默认**不勾**（避免二次重抽与手改冲突）；「同步角色条目」仍默认勾（`_rebuild_stage_items_from_script` 已由 `revision_applied` 触发，面板里只是展示）。

### 16.4 统一带来的产品收益

1. 用户只看到**一个**弹窗：既确认"改了什么/删了什么"，又选择"更新到哪里、怎么跑"；不再出现"应用修改后以为完事、其实下游没跑"的落差。
2. 成本守卫、合并策略（§7）、失效计划校验（§9）只在**一处**实现，两条入口不会出现口径分裂。
3. AI 修改路径不再需要额外的计划模型调用（复用修订结果），比"两条各做一套"更省。

### 16.5 顺手要修的一个小缺口（属统一流程的一部分）

当前介入链只在 `statusMap.storyboard == "reconfirm"` 时才 `refreshArtifacts`（`WorkflowPanel.tsx` 的 `scriptStructureChanged` 判定）。若会话中**分镜还没跑过**，应用修订改了角色集合后：阶段 2 条目已在服务端重建，但前端"角色"页仍显示旧条目，直到用户刷新或触发别的一次同步。

统一流程里应改为：**任何剧本阶段写入成功（手改 PATCH / 应用修订）后都无条件 `refreshArtifacts: true`**（只读 `GET /status`，不触发执行），与手改路径一致。
