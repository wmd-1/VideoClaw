## 0. 一页结论

推荐采用 **“自动调度服务 + 兼容实例池 + 公平等待队列”**，放在 VideoClaw 后端内部，复用现有 PostgreSQL。**资源池是默认开启的生成路径（true + auto），不是需要用户另行打开的可选功能；未就绪时引导配置，manual 仅作为显式高级入口。** 首期不引入 Redis、Celery、Kubernetes 或独立调度平台。

用户体验变为：

> 选择生成方式和画质 → 使用默认生成池（可改选兼容的池）→ 点击生成 → 系统在选定池内分配空闲实例；池内都忙则等待。

“实例池”是管理员管理资源的方式，不应成为普通用户必须学习的新概念。页面默认显示“自动分配”，不要求用户选择服务地址或实例编号。

| 决策 | 理由 |
|---|---|
| 默认开启资源池，开关与就绪分开 | 新装进入 auto；资源未配齐给引导，不访问示例地址或隐式转 manual |
| 会话只存显式选池偏好，执行保存解析快照 | 系统 fallback 不变成用户永久选择，已入队批次仍不跨池 |
| 临时未就绪继续原池等待，显式下线提前结束未派发项 | 既容忍短暂维护，也避免明确停用后无意义地等待一小时 |
| 一个视频片段调度一次，不按整个项目独占实例 | 避免大项目把其他用户长时间挡在后面 |
| 等待队列留在 VideoClaw | 避免把几十个片段提前塞到一个模型服务的队尾 |
| 数据库原子占位 + 远端忙闲探测 | 占位防项目内竞争，探针发现外部负载；查询不能替代互斥 |
| vLLM-Omni 默认改异步，SGLang 保持异步 | 尽早拿到作业 ID，分别管理提交、查询和下载 |
| 只在相同生成契约的实例间切换 | 不为了找空闲实例而换权重、降画质、丢参考图 |
| 专用实例优先，共享实例尽力避忙 | 保留其他工具直连，但明确不能完全消除外部竞争 |
| 池配置独立运行时 YAML，.env 只放开关与路径 | 嵌套结构清楚；改池只改一个文件，管理员在线保存热生效，避免 env 扁平与只读限制 |

效果边界：减少用户选错实例、排错队造成的等待，提高多个实例的利用率；不能缩短模型本身的推理时间，也不能在全部兼容实例繁忙时消除排队。

## 1. 已确认需求与建议边界

### 1.1 用户已确认

- 视频实例约 1–8 个，每个只能承担单并发生成。
- 有专供 VideoClaw 的实例，也有被其他工具共同使用的实例。
- 其他工具继续直接调用共享实例，不强制改走统一网关。
- 推理源码位于 `/home/wmd/projects/vllm-omni`、`/home/wmd/projects/sglang`。
- 若有利于调度，允许将当前 vLLM-Omni 调用改为异步；本方案采用该方向。
- 样例扩为 4 个 vLLM-Omni、4 个 SGLang 自部署实例，在 `.example` 中明确实例归属；配置档与配置支持管理员账号在线修改。
- 项目尚未投产，资源池模式默认开启，不需要按历史项目或存量字段保留迁移分支。
- 未来可能接入 Pika-H3-Flex 等自定义 Docker 推理部署。

### 1.2 本方案建议

- 资源池模式默认开启：`.env` 的 `VC_VIDEO_DISPATCH__ENABLED` 缺省 true、运行时 YAML 的 `default_mode` 缺省 auto，会话 `video_dispatch_mode` 缺省 auto。开关与池文件路径只在 `.env`，池与策略只在运行时 YAML。manual 保留给模型测试、排障、池外模型及当前样例未覆盖的沙盒 t2va，默认隐藏在“高级：手动指定模型”。
- 不增加“每用户只能运行一个任务”或每日配额，通过派发顺序实现公平。
- 保留当前后端单进程部署前提；多个模型实例不等于多个 VideoClaw 后端实例。
- 不跨不同权重、不同效果档位自动降级，不自动切换付费供应商。
- 不实现后端重启后的工作流自动续跑；资源占位恢复与业务自动续跑分开。
- 后续代码按 video-resource-pool-dispatch 的 tasks 分批实施并验收；当前仅工件与样例校验交付，没有把任务勾选为已实施。

### 1.3 共享实例的保证等级

| 范围 | 可以保证 | 无法保证 |
|---|---|---|
| 专用实例 | 经统一调度的 VideoClaw 请求最多占一个名额 | 无法防止管理员在系统外误启动生成 |
| 共享实例 | VideoClaw 不重复占位，发现外部忙则不提交 | 外部工具可能在探测之后抢先提交，仍产生远端排队 |

共享实例标为“尽力避忙”。如果以后要求严格全局单并发或确定排队次序，需要所有调用方共享准入机制，或服务端提供原子预约接口；单靠忙闲查询做不到。

### 2.3 对忙闲参考文档的补充

保留原参考文档不修改，新方案不能直接照搬其中演示代码：

1. **vLLM-Omni sync 不进入作业列表。** create_video_sync 直接生成字节，不写 VIDEO_STORE；list_videos 只读 VIDEO_STORE。其他工具走 sync 时，仅列表为空不能证明空闲。
2. **列表必须考虑分页。** 只读最新 100 条可能漏掉较早的运行作业；扫描不完整应为 unknown。
3. vLLM-Omni 失败作业单查可能返回非 2xx，需要解析匹配该作业的结构化失败体，不能全部按网络故障处理。
4. vLLM-Omni 删除会尽力中止引擎，但当前 batch 可能仍在排空；deleted=true 或后续 404 不代表 GPU 立即空闲。
5. SGLang create_video 在准备请求后写 VIDEO_STORE，启动后台作业再返回 VideoResponse；异步不意味着上传与预处理瞬时完成。
6. **SGLang failed 也可能仍占 GPU。** 删除接口源码明确：scheduler RPC 超时可能使作业标记 failed，但仍在 GPU 上运行。删除发布取消后返回 deleted，同样不能用作释放确认。
7. H3 使用 SGLang diffusion 指标，不是 LLM 指标；需开启 metrics，并匹配真实 role/replica。
8. “没匹配到指标就返回 0”“finally 无条件释放锁”“TTL 到期直接释放”都不适合作为生产准入实现。

## 3. 架构与三层资源模型

```text
Workflow / Regenerate / Sandbox / Pipeline / Model Test
                         |
                         v
             Video Generation Service
       fixed contract + trusted owner/execution
                         |
                         v
              Fair Queue + Dispatcher
                         |
              PostgreSQL jobs / slots
                         |
                         v
             Qualified Idle Instances
                  /      |      \
             vLLM     SGLang    Custom Worker
```

### 3.1 生成配置档：定义“生成什么”

`video_profiles` 中的一条配置档在本方案中就是一个逻辑 **pool（生成池）**，没有另一套独立的 pools 配置。profile 定义模型家族、权重/adapter 修订、提示词契约版本、采样契约版本及输出能力；其 `instances` 列表定义该池的成员。

管理员可以维护“H3 标准”“H3 Flex”等档位，也可按协议/任务拆池；普通用户使用默认池或选择另一个兼容池，随后由系统在池内挑实例。不同池不因模型家族相同而自动互通。

- 不把 H3 原版、Turbo、FastH3、Pika H3 Flex 当作完全等价。
- vLLM-Omni/SGLang 协议不同不必然禁止同池，但必须通过相同生成契约的验收；相同 seed 也不承诺逐像素复现。
- fl2va/ref2va partition 可以分开部署。按模式定义契约、筛选成员，不对整个池 tasks 简单求交集。
- 同模式的契约固定；成员必须完整满足，不能因有空而降分辨率、改时长、丢弃参考输入。

### 3.2 实例：定义“请求发到哪里”

实例引用既有自定义模型，复用 provider 的协议、Base URL 和凭据，不复制另一套密钥。

字段包括 instance_id、model_id、resource_key、access_mode=exclusive|shared、enabled、driver、probe。

提交、查询、下载都绑定同一实例地址，不能在多个进程本地作业仓库之间轮询负载均衡。两个端口或两个模型名不自动代表两份算力。

### 3.3 物理资源槽：定义“谁互斥”

显式 `resource_key` 标识单并发资源，首期每个资源固定一个槽。

- 多模型别名指向同一进程，必须共享资源键。
- 多个进程实际共享同一组不能并发使用的 GPU，也共享资源键。
- 配置校验检测重复端点和资源声明冲突；DNS 别名、GPU 拓扑由管理员核对，不能仅凭 URL 推断。
- 1–8 指独立资源槽数量；同资源多个实例定义不能重复计容量。
- 即使多个 profile 引用同一实例，仍共享同一 resource_key 的全局槽位；pool 边界不能用来绕过互斥。本次样例为四个不重叠的池。

## 4. 用户选择、配置样例与兼容

### 4.1 显式选择字段

新增 `video_dispatch_mode=auto|manual` 和 `video_profile_id`，不把字符串 auto 冒充真实模型 ID。**会话的 video_profile_id 只存用户显式选池偏好，默认 null；管理员推荐和 fallback 结果只写执行快照，不回写会话。** 用户可选择“使用推荐池”清空显式偏好；profile revision、选池来源和有效契约在每次受理执行时固定，不能以持久化字段非空推断选择来源。

缺省值：全局开关 `VC_VIDEO_DISPATCH__ENABLED=true`（读 `.env`），运行时 YAML 的 `video_dispatch.default_mode=auto`；会话 `video_dispatch_mode=auto`。未选池时按 §4.1.1 解析。manual 只在用户展开“高级：手动指定模型”或点击“本次改用手动模型”并确认后使用，不是未就绪时的自动回退。

实施时必须同版对齐四个来源，不能只改本 `.example`：

| 来源 | 必须落地的默认值与守卫 |
|---|---|
| backend/config.py 与 `.env.example` | 开关 `VC_VIDEO_DISPATCH__ENABLED` 缺省 true；`VC_VIDEO_PROFILES_FILE` 指向运行时 YAML；被 env 覆盖时设置页只读并标来源，保存不写回 env |
| core/video_pool_config.py 的运行时默认 | `default_mode="auto"`、`default_profiles={}`、`video_profiles=[]`、`video_instances=[]`、`queue_timeout_seconds=3600`、`max_queued_jobs=1000`、`max_running_jobs=8`；默认常量不得含推荐池 ID |
| ProjectStartRequest、会话参数解析/持久化/恢复 | 字段缺省按 auto，显式 manual 才走手动；不因出现具体模型字段而推断手动 |
| HomePage.tsx、TopBar.tsx、WorkflowPanel.tsx | 首页、顶栏、恢复三处统一 auto；不使用具体视频模型 ID 或列表首项作默认 |

当前 config.py 与请求 schema 尚无这些字段；本轮仅修订设计/样例，代码默认值和前端行为均列为待实施。必须按 `video_dispatch_mode` 分支，而不是按模型字段是否为空分支：

- backend/api/routers/workflow.py 的 `_require_model_fields`、`_preflight_stage_models`（整阶段及介入重生成均调用）都要接入统一模式解析。auto 不调用 `_active_video_model` / `_active_video_model_field` 获取会话或 settings 默认模型；manual 才消费这条具体模型来源链，非视频校验不变。
- **auto 最终仍调用具体实例，但具体模型只能来自统一就绪解析器给出的候选集及派发器选择结果**，并记录进执行上下文/attempt/派发凭据；不能从会话 `video_*_model` 或 settings 回退取值。预检读取配置与已缓存的资格/观测，不发即时探测，更不生成。
- auto 的解析结果不得回写会话 `video_model`、`video_first_frame_model`、`video_start_end_model`、`video_reference_model`。这些字段保持空或原有手动值不动，auto 不消费它们；Agent 层的默认填充与 `_select_video_model` 等路径同样不能重新取回 settings 绕过池。
- auto 必须绕过 `_select_video_model` 及其缺模型异常，也不能继续使用 `get_max_concurrency(video_model, ...)` 决定视频批次并发。video_agent.py 的正常生成和重生成均批量入队轻量作业，池执行上限与瞬时可派发名额按 §5.2.1 分开计算。models/config_model.py 的单模型并发函数在视频侧只供 manual 使用，图片侧既有行为不变。
- 项目创建默认填充、会话更新白名单、执行和重生成参数合并、后台任务、模型测试需同步接线。预检输出与派发消费同一契约，但实例占用仍到派发才原子获取，不在预检提前选死服务器。
- HomePage.tsx 不仅要修改 modelConfigReady，还要修改加载配置时因缺具体视频模型提前抛错的分支；TopBar.tsx、WorkflowPanel.tsx 的恢复/参数合并也按模式处理。LLM、图像等校验不放宽，首次配置入口不能随生成按钮一起被禁用。
- ModelFallbackDialog.tsx 按模式与错误码呈现池等待/未就绪/不兼容/停用；lib/workflowApi.ts 保留结构化 detail、缺项和 actions，不能仅识别 model_unavailable 后将其他错误降成字符串。config/models.ts 的具体模型字段映射只供 manual，auto 使用池契约；图片阶段现有提示不随之改变。

首次启动的资源池最小默认片段（运行时 YAML 为空资源，开关在 `.env`）：

```yaml
video_dispatch:
  default_mode: auto
  default_profiles: {}
  queue_timeout_seconds: 3600
  max_queued_jobs: 1000
  max_running_jobs: 8
video_profiles: []
video_instances: []
```

`.env` 的 `VC_VIDEO_DISPATCH__ENABLED` 缺省 true，`VC_VIDEO_PROFILES_FILE` 指向该文件，两者见 `.env.example`。运行时加载器对缺失文件返回上述空默认，不把空文件当错误；`video_dispatch.enabled` 出现在 YAML 属配置错误，避免“env 已关闭、YAML 仍写 true”的双来源。

运行时默认用同结构深合并，默认常量不得含推荐池 ID，避免空字典被深合并带回悬空推荐。default_profiles 省略时规范化为 `{}`；按方式没有键表示正常的“未设置推荐”，直接解析首个就绪兼容池。非字典、空字符串值、非空但不存在的池 ID 或未声明对应方式属于配置错误，保存拒绝并列字段路径；不能把悬空 ID 静默当作未设置。八实例样例保留三个方式映射、两个不同推荐 ID，因其四个 profile 实际存在。

既有 video_first_frame_model、video_start_end_model、video_reference_model 保留给手动模式。

统一解析器输出：模式、有效参数、profile 版本、候选实例、输入要求、错误原因。

- 改写、时长归一、生成、UI 参数联动读同一有效契约。
- 手动选择受管模型仍经过同一队列和占位，不能绕过。
- 池外模型可经高级 manual 入口调用，但不凭空获得受管资源的全局互斥保证；能映射到受管 resource_key 的别名仍须占用同一槽。
- auto 按 §4.1.2 分别处理未就绪、参数不兼容和繁忙，不偷偷改选模型。
- 配置补齐后，保持 auto 的会话无需用户切换模式，新执行自动进入池内调度；不会自动发起生成，也不会覆盖用户明确选定的 manual。引导中的“本次改用手动模型”仅覆盖当前提交，不把会话默认持久化为 manual。
- 不把瞬时忙闲塞进 `/api/models` 或 model_availability() 的“配置可用”含义。

### 4.1.1 四个 pool 时如何选择与调度

**用户可以选择 pool，但每次执行只能绑定一个 pool；自动调度发生在这个选定池内。** 选择 pool 仍属于 auto 模式，manual 表示直接指定具体模型/实例，两者不要混淆。

1. **新执行选池**：用户显式偏好非空则只校验该池，不替换；无显式偏好时，先取当前方式已配置且就绪兼容的管理员推荐池，再按配置列表顺序取首个就绪兼容池。**默认池 busy 时仍选默认池排队，即使其他池空闲也不改选**；实时 unknown/unreachable 也不改变选池，仅按 §6 的 access_mode 分档决定是否等待。减少排队依靠池内多实例，跨池追逐空闲不在本期范围。
2. **推荐预览不等于用户选择**：下拉默认显示的系统推荐仅为展示，不能当作用户选择保存或随创建请求写入偏好；只有用户主动选池才提交 video_profile_id。无推荐映射时返回 has_default_recommendation=false，文案“未设置推荐池，已选择 X 池”是普通信息；有推荐但未就绪时才提示“默认池未就绪，已改用可用的 X 池”，不兼容则写明不兼容。每次新执行重新解析，因此先前自动 fallback 的 X 下线后可回到已就绪默认 Y，并提示“原自动分配池不可用，本次已改用 Y 池”。上次结果仅从执行记录读取供展示，不成为持久化偏好。
3. **受理后绑定**：入队事务固定 execution_id、profile_id、profile_revision、selection_source=user|admin_default|fallback、契约/输入/成员快照。selection_source 由后端计算，仅用于执行审计与展示，不接受客户端自报，也不是会话配置字段。fallback 明确定义为“未采用管理员指定池而确定性选取首个就绪兼容池”，包含正常无推荐（recommendation_reason=no_default）和推荐未就绪/不兼容两种情形；它本身不是异常，不据此触发告警。即使尚未提交远端，已入队批次也不能重新选池；可用集合 = 快照记录实例 ∩ 当前仍属于该池且满足原契约、enabled/资格有效的实例，再按 resource_key 去重。新加成员不进入本批次，被移除成员不再接收其新片段。
4. “生成配置 → 生成池”标明兼容性与 ready/not_ready/busy。not_ready 项展示缺项且不可提交；用户显式选择的不可用池保留该选项及缺项原因，不代表预留任何资源槽。四池均就绪兼容时可选四池之一，busy 仍可选并排队。
5. 用户可在下一次执行前改选或清空显式偏好，重新校验参数、有效时长和提示词新鲜度；进行中的批次不受影响。要替换已排队/运行批次的池，必须停止后重新提交，旧尝试仍按原实例核对。显式偏好与新生成方式不兼容时给出选择建议并拒绝提交，不静默改选。
6. 显式选择的池被删除或不就绪，保留所选池与原因，用户改选或清空偏好后继续。系统推荐没有持久化偏好，不会因此卡在上次 fallback；管理员修改推荐只影响无显式偏好的新执行，不修改已受理快照。
7. 已入队后池临时变 not_ready 按 §5.4 继续原池有限等待；管理员显式下线池则按 §5.4 提前终止未派发项。两者都不跨池。

本样例的默认值是 SGLang 首尾帧池/参考图池，管理员可改成对应 vLLM-Omni 池。选择的是池，不需要选择池内的 01/03 或 02/04 实例。

若目标是“同一任务尽可能使用两种协议的全部等价实例”，应由管理员在验收等价后把这些实例放进同一个 pool；不是让运行中的作业跨四个独立池随机跳转。首期只做新执行的确定性推荐，不做已受理批次跨池调度或自动降档。

### 4.1.2 默认开启、就绪判定与降级

以下三个维度独立，不把“开启”“选择 auto”“现在能派发”压成同一个布尔值：

| 维度 | 缺省/来源 | 含义 |
|---|---|---|
| 全局开关 `VC_VIDEO_DISPATCH__ENABLED` | true（`.env`） | 允许受管资源接受新派发，不代表存在可用资源；改值需重建容器 |
| 会话模式 video_dispatch_mode | auto | 使用选定池；manual 必须由用户显式选择 |
| 池就绪 | 运行期派生，不写配置 | 池允许接单、契约完整、引用有效、无占位值，并至少有一个启用且具有当前修订资格证据的匹配实例 |

就绪按 pool 和其声明的生成方式判定；部分实例未启用不否定其余合格成员，容量按合格 resource_key 去重。一池可先上线一个合格实例，示例清单启用两个是为得到双实例容量，不要求全部八个实例同时合格。就绪之后仍需通过 §6 的实时探针和 §7 的原子占位，不能以资格证据替代实时准入。

auto 请求的处理顺序与行为如下；用户确认 manual 后按 §6.1 的显式手动准入执行，不继续走零就绪池拦截：

1. **全局关**：返回 dispatch_disabled，显示运维停用提示，按 §9.3 停止新派发，不隐式改 manual，不通过改名绕开占位。
2. **全局开但全系统零就绪池**：无用户显式偏好时返回 409 pool_not_ready 和缺项，不创建调度作业、不占槽、不进入资源等待队列，不启动生成。有显式偏好则优先返回该池的 selected_pool_not_ready 或 pool_unavailable，并提供同一配置引导；错误码及 HTTP 包装统一按 §10.4.2。不得将首次配置问题呈现为 generic model_unavailable 或让页面无入口地停摆。
3. **首次配置引导**：“资源池已开启但暂无就绪实例，可让管理员完成配置，或本次改用手动模型”。提供“管理员完成配置”和“本次改用手动模型”；前者对管理员打开配置页，对普通用户说明需联系管理员而不授予写权限。后者展开具体模型选择，用户确认后才生成一次 manual 请求。关闭弹窗不改模式，不存在自动转 manual 或绕过确认重发。按 §10.1 的提交尝试去重，SSE/轮询重复结果不会反复弹窗。
4. **有就绪池，但与本次方式/参数不兼容**：返回 pool_incompatible，列明 task/画幅/时长等不匹配原因，不降参数，不冒充“全系统尚未配置”。用户显式所选池未就绪返回 selected_pool_not_ready，保留偏好与缺项；若被管理员明确下线则为 pool_unavailable。没有显式偏好的新执行按 §4.1.1 重解，已受理的执行按 §5.4 等待/终止而非重解。
5. **所选池就绪但槽已满**：正常排队；busy 不等于 not_ready。探针 unknown/unreachable 独立显示：shared 阻止派发并有限等待；完成启动核对、无异常遗留的 exclusive 不以普通观测缺失/陈旧为派发闸门，按 §6 执行。
6. **配置补齐**：刷新运行期状态后，auto 的新执行自然使用就绪池，无需用户另开模式；没有提交的请求不会自动启动，已固定池/明确选择 manual 的请求也不被修改。

占位安全与状态接口：

- 保存草稿允许占位配置，但启用或网络访问前必须按 §4.1.3 的字段级规则检查；占位地址或必需字段未补齐时拒绝生效和派发，不扫描注释/显示名称，也不靠任意子串匹配。
- 不能要求先 ready 才允许做资格验证，否则会形成循环：管理员填好真实地址与契约后，可以在实例尚未启用时显式发起资格检查；只读检查与经确认的真实生成测试分开，后者仍经同一资源占位。未就绪时禁止的是自动探测占位地址，不禁止管理员校验已补齐的真实实例。
- GET /api/video/profiles 按 §10.4.1 返回 dispatch_enabled、has_default_recommendation、每池 state、dispatchable、observation 与缺项。state 表示配置资格及忙碌摘要，dispatchable 才是“当前快照是否允许派发”，两者不能混用。
- GET 只读缓存/运行期派生，不因浏览器读取接口而即时探测。管理员可看具体字段缺项，普通用户只看不包含地址/凭据的摘要。
- 就绪状态不写运行时 YAML，资格证据仍存现有拟议的 DB 元数据；配置修订变化使旧资格失效，实时 busy/unknown 不修改文件。
- enabled=false 是运维级停用：只停止新的受管派发，具体排队/在途收尾见 §9.3；它不清空占位，也不关闭必要的在途核对。

### 4.1.3 占位值的精确校验与草稿边界

只处理 YAML 解析后的指定字段，既不搜索整个文件文本，也不检查注释。参与判定的字段与规则如下：

| 字段 | 必填与占位判据 |
|---|---|
| api_providers[实例引用供应商].base_url、实例 probe.jobs_url、按 probe.kind 要求的 probe.metrics_url | 必填 HTTP(S) URL；先解析 hostname、按 IDNA 转 ASCII、小写并去末尾根点，等于 `example` 或以 `.example` 结尾才命中示例域名。`api.example.internal` 不因含 example 被拒；仍执行正常地址安全校验 |
| 实例引用的 custom_models[].model、profile.artifact_revision / prompt_contract_revision / sampling_contract_revision | 要求明确非空值；字符串去首尾空白后转大写与 `CHANGE_ME` 完整相等才算占位，不做包含匹配 |
| video_instances[].resource_key | 必须非空，完整值 CHANGE_ME 或大小写无关的正则 `^example-gpu-[0-9]+$` 判样例资源键；实际相同 GPU 必须填写相同真实键 |
| SGLang probe.labels.role / replica | 对该探针必填、非空；按完整 CHANGE_ME 标记判占位，不以 replica=0 为默认猜测 |

所有上述字符串字段均拒绝完整 CHANGE_ME；缺值、非法 URL/枚举/数值和引用悬空是独立的 schema/完整性错误。profile.id、instance_id、显示名称不因含 example 而失败；api_key 允许空且不纳入占位启用清单。无须 metrics 的驱动不强制填无意义 URL。

- **保存草稿**：实例 enabled=false 时可保存未填的上述值并返回缺项；对应池不就绪，但其他合格成员不受禁用草稿阻塞。profile 必需契约不完整则该 profile 整体不就绪。引用结构/字段类型本身仍必须合法。
- **启用/修改生效**：将实例设 true 或修改正在启用实例的相关配置时，在写入前统一校验；不合格返回 400 配置错误及字段路径，文件和内存均保持原值。不能只保存 true 再让线程尝试请求。
- **文件手工写入后的加载**：可载入并展示该不合格条目以便修正，但其有效启用状态为 false、附缺项，不将它用于派发/后台探测；不自动改写配置文件。
- **网络访问兜底**：派发、普通 manual 和管理员资格检查共用字段检查；显式资格验证允许目标实例尚为 false，但不允许占位目标。已有资格不掩盖配置变更，相关修订变化使资格失效。

### 4.2 运行时文件、样例与 `.env`

采用 [backend/video_profiles.yaml.example](../../video-claw/video-claw/backend/video_profiles.yaml.example) 作为样例。运行时文件由 `.env` 的 `VC_VIDEO_PROFILES_FILE` 指定；Docker 下为 `data/config/video_profiles.yaml`（容器内 `/app/data/video_profiles.yaml`），宿主已有 `./data/config:/app/data` 挂载，不新增 Docker 挂载，也不新增独立服务。

分工固定为：

- `.env`：`VC_VIDEO_DISPATCH__ENABLED`（缺省 true，全局开关）与 `VC_VIDEO_PROFILES_FILE`（路径；未设置时默认 `CONFIG_PATH.parent/data/video_profiles.yaml`，Docker 下即 `/app/data/video_profiles.yaml`）。被 env 覆盖的字段在设置页只读并标注来源；改开关需重建容器，改池不需要。父目录不可写时保存失败并提示，不自动创建宿主目录。
- 运行时 YAML：`video_dispatch` 的 `default_mode`、`default_profiles`、`queue_timeout_seconds`、`max_queued_jobs`、`max_running_jobs`，以及 `video_profiles`、`video_instances`。**不写 `enabled`**；出现该键属配置错误，避免 env 与文件双来源。
- `config.yaml`：继续保存 providers/custom_models/models 等，不再保存池与实例；因此 provider 密钥仍可用既有环境变量管理。

保存与加载：

- 管理员页面保存走 `PUT /api/video/profiles`：校验后原子写运行时 YAML（临时文件 + rename），更新内存快照并唤醒调度器；新请求生效，无需重启。
- 宿主直接编辑文件时，按 mtime 与内容摘要检测变化并只读重载；解析失败保留上一份有效快照，展示 `configuration_errors`，不派发、不覆盖文件。
- 首次启动文件不存在时返回空池默认（开关仍由 env 决定），不自动复制样例、不自动登记示例地址；主模板无实例时显示“已开启 / 未就绪”。
- 管理页不得整文件覆盖与池无关的设置；池文件只由该页或宿主编辑维护，两者都以 `expected_revision` 防覆盖。

本样例是**设计契约，不是当前版本可直接启用的配置功能**；当前版本即使识别 provider/model，也不具备新实例池保护，不应提前复制启用。

样例约束：

- 每种协议各四条 provider、model、instance 注册，共八实例；四个 profile 各引用两个实例，归属的唯一配置依据是 profile.instances，不再在实例端重复维护 pool_id。完整引用链为 profile → instance → model → provider。
- 地址是保留示例域名，密钥为空，resource_key 和 exclusive/shared 为演示，不冒充真实部署。此文件是固定的教学/回归样例，不兼作 staging 配置；真实地址和修订应写入运行时 YAML，直接修改样例后校验失败是预期保护。
- 全局开关 `VC_VIDEO_DISPATCH__ENABLED=true`（`.env`）、运行时 YAML 的 `default_mode: auto`，八个实例 `enabled: false`：这是“模式默认开、占位地址不启用”。复制为运行时文件后为“已开启 / 未就绪”，按 §4.1.2 引导，不派发、不自动探测示例地址、不排队。
- 权重、提示词、采样修订使用 CHANGE_ME，SGLang replica 也需按真实指标填写，不假定为 0。
- 草稿可保存占位符，启用前必须清除并完成资格验证。资格证据存 DB、绑定修订，不能配置 qualified=true 就算验收。
- 示例只演示主流程 fl2va/ref2va；不声明 t2va。沙盒文生视频需另配真实支持 t2va 的实例。
- 采样默认值不声明不等于两个服务默认相同；启用前核对，必要时显式声明相同语义的采样参数。
- probe.kind 是拟新增的 VideoClaw 探针类型，不是推理服务的新端点。
- 配置解析、coercion、序列化、API 类型与 UI 在后续实施时一并接入，不能保存后丢失新分区。

最小启用清单：替换同池成员的 base_url/jobs_url/metrics_url → 填真实服务端模型名并核对 GPU 资源键 → 清除 CHANGE_ME、补齐契约/标签 → 管理员完成资格验证 → 启用同池两个实例 → 该池就绪并具有两个资源槽。也可先启用其中一个合格实例获得单槽容量，第二个补齐后扩容。

## 5. 队列与派发规则

### 5.1 入队单位与输入快照

一个片段的一次生成对应一个作业；整阶段批量提交轻量描述，不预占实例，不提前塞入远端队列。

保存可信 owner、来源类型、会话/任务 ID、execution_id、片段 ID、幂等键、profile 修订、参数快照、提示词和规范化媒体引用。

- 提示词受个人空间权限保护，不进入全局状态接口。
- 不持久化短期预签名 URL、运行期 `_refs` 路径或凭据。
- 入队检查归属；派发前重新校验、物化并刷新媒体签名，防止排队后过期。
- 已排队作业使用不可变输入快照；后续编辑配置/素材不悄悄改变它，停止重做才采用新输入。

### 5.2 公平且尽量用满资源

1. 先限定到本次 video_profile_id 对应的 pool.instances，再找满足契约、已启用、符合准入条件的资源。
2. 在具有可匹配作业的用户之间轮转，每轮每人派发一个片段；用户内部按会话轮转，同会话按入队顺序。
3. 同一用户开多个会话不增加用户级轮转权重。
4. 所选池有空位且其他用户没有可匹配作业时，同一用户可以继续使用池内剩余槽，不人为闲置可用 GPU；不为填满其他池而越过作业的 pool 边界。
5. 新用户不抢占运行中任务，从下一个释放的兼容槽参与轮转。
6. 优先处理适配范围较窄的空闲资源，再分配通用资源；不兼容队头不阻塞其他可运行作业。
7. 专用实例优先于共享实例；同等级按最近派发时间轮转，首期不采用缺少数据的“预测最快”。
8. enable_concurrency=false 只限制该执行同时在途一个片段，不变为用户级限额。

公平是派发机会公平，不是 GPU 秒数严格均分；外部工具不受本系统公平策略控制。

### 5.2.1 auto 并发来源与动态派发

现有 video_agent.py 在 `_select_video_model` 后调用 models/config_model.py 的 `get_max_concurrency`，全量及介入分支再据此创建 ThreadPoolExecutor；样例单模型 concurrency=1 不能成为 auto 批次的并发上限。

- 新增可选策略：`video_dispatch.max_running_jobs` 缺省 8（全局所有受管在途尝试上限），`video_profiles[].max_concurrency_per_execution` 缺省 8（单执行策略上限），均只接受 1–8 的整数、拒绝 bool。不新增用户配额。
- 批次受理时保存 profile 策略上限；每次派发按快照成员与当前有效成员交集计算合格槽数 C，不扣其他执行占用来固化上限。enable_concurrency=true 时当前执行上限为 min(C、快照策略上限、当前 profile 策略上限、全局策略上限)；false 时最多 1。上限下降不取消已在途请求，只阻止新增到超额。
- **瞬时派发名额**另按 min(本执行上限减其在途数、全局上限减全局在途数、候选实际可派发空槽数) 计算，取非负值。在途含 reserved/preparing/submitting/remote_queued/running/unknown/cancel-draining，不能因用户停止或租约超时漏计仍占资源的尝试；下载发布不计 GPU 在途。
- 当前空闲数为 0 只表示本轮等候，不能把 ThreadPoolExecutor(0)、单模型 concurrency=1 或入队时的 free_capacity 固化到整个执行。资源释放/恢复、配置合法变更会唤醒统一调度器，重新计算名额；任务队列不借用推理线程等待空位。
- 正常生成、单条/批量重生成均直接提交全部轻量片段描述（受全局队列上限约束），由调度器按用户轮转选取；只有拿到资源槽后才准备/提交一次模型请求。首帧/尾帧依赖由输入快照满足，不人为串行。
- manual 视频保留按模型 concurrency 的执行并发策略，但受管实例最终仍以同一资源槽容量 1 为硬上限；get_max_concurrency 的图片消费者不受此次视频策略变化影响。

单用户六片段、三台合格空闲实例、策略≥3 的首轮必须实际产生三个不同实例的在途请求，不能仅验证多个用户合起来能填满池。双实例样例首轮必须产生两个请求；关闭 enable_concurrency 后只有一个，其余等待。

### 5.3 等待和错误

- 首次提交时零就绪池走 §4.1.2 配置引导，不创建作业、不排队、不派发；不是繁忙等待。已受理之后才变未就绪的作业按 §5.4 处理。
- 有就绪池但无兼容的方式/参数组合时明确报 pool_incompatible；显式所选池未就绪则报 selected_pool_not_ready，不混成全局未配置。
- 所选池就绪且兼容但资源全忙：正常排队，不报模型不可用、不触发 Doctor、不自动改选其他 pool。
- shared 已就绪但实时探针异常：显示暂不可派发并有限等待；exclusive 的普通观测异常只展示，不因后台探测退避阻塞正常新派发。存在未核对遗留或异常隔离则两类都等待，按 §6 分档，不能把 unknown 伪装为 idle。
- 本地等待与远端生成超时分开；本地等待默认 60 分钟、管理员可调。受理时固定批次 queue_deadline_at=accepted_at+queue_timeout_seconds；未派发片段统一受这个期限约束，临时 not_ready、探针抖动和重探不暂停或重置计时，详见 §5.4。
- 建议全局最多 1000 条等待作业；容量不足返回 queue_full，整批原子拒绝，不偷偷接收半批。这不是每用户配额。
- 等待只占数据库记录和轻量异步句柄，不占阻塞推理线程或长期数据库连接。

### 5.4 入队后池不可用、超时与显式下线

决策：**短暂不可用容忍到原等待期限；明确下线提前结束未派发项。** 选择这个组合是为了允许实例维护恢复，又避免管理员已确定下线后让用户空等。不能将所有 not_ready 都立即失败，也不能把明确下线当 busy 等满一小时。

| 事件 | 未派发的已受理片段 | 在途尝试与批次收尾 |
|---|---|---|
| 实例停用/排空、资格失效使池临时 not_ready；或 shared 探针异常/任一资源异常隔离 | 保持原池及快照，dispatch.phase=waiting_pool_unavailable，显示“资源池暂不可用”；恢复后仅使用快照实例 ∩ 当前该池仍满足原契约且启用/资格有效的实例。原 queue_deadline_at 不变，不跨池 | 已在途任务继续执行/核对，不因本池临时未就绪自动取消 |
| 原等待期限到达 | 未派发项 failed，error_code=queue_timeout；显示“等待资源超时，已完成内容已保留” | 已提交/不确定提交继续原实例核对；不重发、不释放他人的资源槽 |
| 管理员显式下线整池 | 下线生效即阻止新受理/派发，未派发项 failed，error_code=pool_unavailable；不等期限 | 在途仍可完成、下载与核对，保留成果及资源占位直到确认结束 |
| 关闭全局 `VC_VIDEO_DISPATCH__ENABLED`（改 `.env` 并重建容器） | 按 §9.3，以 dispatch_disabled 停止全部未派发的受管作业 | 按运维停止结账，已在途仍安全收尾 |

首行在途尝试继续执行/核对；temporary not_ready 不自动取消它们。队列失败后若仍有在途项，批次保持执行中并在摘要显示失败数量，待在途均可结账后，含 queue_timeout/pool_unavailable 的正常批次以执行 failed、阶段 error 收尾；保留成功片段和已有 versions/selected。用户停止/全局运维停止优先按既有 interrupted/stopped 收尾；后台单项仍按既有产物重算，不把新错误码写成阶段状态枚举。

显式下线使用管理员动作，将可选配置字段 `video_profiles[].enabled` 设为 false（缺省 true，表示允许接单，不等于就绪），并记录操作者/影响范围；这与某个实例 enabled=false 不同。下线与最终提交授权使用同一进程内闸门，在既有配置保存锁下先持久化并替换禁止派发快照，再清理等待项；不能把 YAML 与 DB 操作声称为同一事务。已获发送授权的尝试视为在途，尚未获授权者看到新标志后停止；重启时按持久化标志补做幂等收尾。该字段属于已有 profile 配置层，不新建资源模型或数据库表。重新启用不复活已失败/停止批次。八实例样例可省略池级 enabled，八个实例仍为 false。

判定“未派发”需在派发互斥/事务中确认未跨过 submitting 边界；reserved 名称本身不是证据。任何已经发送或无法证明未发送的请求均按在途保留占位。首次提交前无就绪池仍按 §4.1.2 拒绝，不能为了使用本节等待而先创建作业。

## 6. 忙闲探针与准入

### 6.1 三种状态分开

- 管理状态：启用、排空、停用。
- 项目内占位：空闲、已预留、生成中、待核对。
- 外部观测：idle、busy、unknown、unreachable，以及时间和覆盖范围。

auto 可派发必须首先满足 §4.1.2 的池就绪判定，再同时满足全局开关开启、所选池契约兼容、具体实例启用、启动核对完成、本地无占位/异常隔离，以及下表的 access_mode 准入。所有 auto 入口共用同一解析器，不将“实时探针通过”当成两类实例共同的逐次条件。

| access_mode / 场景 | 准入规则 |
|---|---|
| exclusive 正常态 | 管理员已确认独占、资格有效、当前 boot 启动核对完成且无未决尝试时，空槽可直接原子预留并派发，不等周期/按需忙闲探测；普通 probe unknown/unreachable/stale 仅用于健康展示 |
| shared | 本地空槽还不够；需两次近期独立 idle 观测、间隔至少 5 秒、均未超过 15 秒，再在预留后/提交前刷新确认 idle，单轮探测总预算 3 秒；缺失、失败、陈旧或忙都不提交 |
| 两类异常态 | 重启待核对、提交结果未知、取消未确认或与账本矛盾的可靠忙碌证据，必须隔离并核对到可证明结束；不能仅凭 exclusive 声明或 TTL 清除 |

exclusive 的放行依据是已核对的独占账本，不是把 unknown 解释为 idle。若可靠观测显示本地无作业却有生成正在进行，视为独占前提失效/潜在遗留，进入异常核对并提示管理员；不能继续当作普通健康展示忽略。首次纳管和每次后端启动均完成一次遗留核对，普通请求不重复做该核对。实际提交错误仍走 §8 的确定性/未知分类，不受本条豁免。

显式 manual 不以某个 profile 已就绪为前提，否则首次配置引导和管理员资格测试都会循环阻塞；但仍须检查模型/地址/输入合法性。受管 manual 继续受全局停用闸门、统一资源槽和对应的探针安全策略约束，不能因没有 profile 就免占位。未启用实例只允许管理员显式资格检查流程访问已补齐的真实服务，普通 manual 不得借此调用禁用实例，任何入口都不访问占位地址。

本地有占位时 metrics=0 不能释放；shared 外部 busy 时不能提交，exclusive 无账本对应却观察到可靠 busy 时进入异常核对。两种计数不相加，避免本系统作业重复统计。

### 6.2 探针选型

| 服务 | 观测来源 | 边界 |
|---|---|---|
| vLLM-Omni 异步作业 | 完整扫描 `/v1/videos`，已知作业单查 | 列表只覆盖异步，每实例单 API worker |
| vLLM-Omni 共享实例 | 经验证的 running/waiting 指标，列表补充 | 外部使用 sync 时仅列表不能判 idle |
| SGLang diffusion | diffusion running/queue，作业查询补充 | 开启 metrics，精确匹配目标 role/replica |
| 自定义服务 | 驱动声明的容量/活动作业接口 | 不假定 Docker 镜像天然带 HTTP 状态接口 |

- vLLM-Omni 目标指标为 `vllm_omni:num_requests_running`、`vllm_omni:num_requests_waiting`。
- SGLang 目标指标为 `sglang:diffusion_num_running_reqs`、`sglang:diffusion_num_queue_reqs`。
- 健康检查、TCP 连接或 `/v1/models` 成功都不能证明空闲。
- Prometheus 解析支持 label、浮点和科学计数格式；缺序列、NaN、负数或非预期值、HTML 响应均为 unknown，不返回默认 0。
- 列表扫描遇到时间/页数预算上限、游标异常或中途失败则为 unknown。
- 共享实例必须验证探针覆盖外部实际调用路径，包括 sync；覆盖不足可以登记展示，但不参与自动派发。
- 专用实例按 §6.1 使用核对后的本地登记准入；普通健康探针不是首单等待条件，但首次纳管、启动及异常恢复须确认无遗留任务。健康展示路径与遗留核对路径分开，不能只清空登记。

### 6.3 频率与负载

- 只对已启用、配置完整且地址非占位的实例做后台探测：有等待作业每 5 秒，无等待每 30 秒。首次配置引导与禁用占位实例不会触发周期探测；管理员资格检查按 §4.1.2 显式执行。
- 单轮探测总预算 3 秒（包含需要的分页/多端点查询），同实例 singleflight 合并；浏览器只读接口不触发探测。
- shared 的新批次入队会唤醒按需探测：缓存陈旧/观测不足时不等空闲轮询的 30 秒；若处于错误退避，可合并执行一轮提前检查，但同实例两轮按需检查至少相隔 5 秒，失败后仍保留 15–60 秒后台退避，不能靠反复点击无限绕过限频。
- 提前检查成功后清除失败退避，但不足两次 idle 时至少等到下一次间隔达 5 秒的检查；资格有效且两次均新鲜后才预留并做提交前刷新。此次确认也是同实例合并的一轮、预算 3 秒，失败只释放已证明未提交的预留，不发送生成。
- exclusive 正常首单不做按需探测、不等退避；只有启动/异常核对或管理员显式诊断会按需检查。实际生成调用不是健康探针。
- 观测超过 15 秒即陈旧，不用于 shared 准入。两次 idle 加最终复查仍是软闸门，无法消除外部直连竞态。
- 周期检查失败按 15–60 秒退避，以上按需调度具有有限优先权；不以真实生成请求恢复健康。
- metrics_url 与 jobs_url 分开解析，保留代理路径前缀，不盲目拼成 `/v1/metrics`。

## 7. 原子占位与持久化

### 7.1 最小数据结构

沿现有 db/migrations 新增迁移，建议三张表：

| 表 | 核心数据 |
|---|---|
| video_dispatch_jobs | owner、来源、execution_id、片段、输入快照、状态、幂等键、取消标记、时间 |
| video_dispatch_attempts | instance/resource、配置修订、远端 ID、提交确定性、错误、计时、结果位置 |
| video_resource_slots | resource_key 唯一行、当前 attempt、token、boot_id、心跳、待核对状态 |

配置档/实例声明由管理员通过运行时 YAML 管理；瞬时忙闲和作业状态不写回该文件。部署资格证据属于运行期元数据，可关联资源与配置修订保存，不由普通配置字段自报。

### 7.2 原子派发步骤

1. 短事务锁定槽位并条件更新，只有空槽能绑定 attempt。
2. 作业 queued→reserved 与绑定槽位在同一事务完成。
3. 提交事务后再物化、复查探针、调用 HTTP，不持锁等待模型。
4. 发请求前再核对取消、execution_id、配置修订、槽位 token。
5. 回调只有匹配 attempt/token 才可更新或释放，旧回调不得释放后来者。
6. 所有受管生成入口统一接入；底层发送前验证派发凭据，缺凭据拒绝。

### 7.3 生命周期

```text
queued --> reserved --> submitting --> remote_queued/running
   |           |             |                    |
   v           v             v                    v
cancelled   cancelled      unknown       remote_terminal --> downloading --> succeeded
                              |
                              v
                         reconciling
```

作业终态与资源状态分离：业务已停止时资源可能仍 draining；远端结束时本地下载可能未完成。

- 正常完成且驱动确认计算结束后释放推理槽；下载、MinIO 发布不占 GPU 槽。
- failed 只是作业 API 状态时不能直接释放，尤其是 SGLang scheduler RPC 超时；需引擎排空证据或管理员核对。
- deleted、404、传输异常、超时不是释放凭据，不能在 finally 无条件释放。
- 建议心跳 30 秒、失联判定 90 秒；失联只触发核对，不自动回收许可证。
- 无法确认停止时保持隔离并提示管理员，不靠 TTL 猜测。
- token 只隔离本项目回调，不等于推理服务支持分布式 fencing，不解除单后端约束。

## 8. 异步协议、重试与独立控制

### 8.1 明确采用异步

**将当前 vLLM-Omni 视频调用默认改成异步作业模式**，不再 sync 优先后再回退 async：

```text
POST /v1/videos
  --> persist job_id
  --> GET /v1/videos/{id}
  --> GET /v1/videos/{id}/content
```

- 新增 custom_models[].video_api_mode=async|sync，vLLM-Omni 缺省 async；现有默认调用也采用此行为，不仅新 profile。
- 若确需同步协议做模型排障，由管理员对池外 vLLM-Omni 模型显式选择 sync；这是独立协议控制，不是存量迁移分支。一次请求不自动探测/回退协议，首期入池的 vLLM-Omni/SGLang 必须 async。
- SGLang 保持异步并接入生命周期，首期只接受 async，不提供未经实现的 sync 选项。
- 对同步 Python 调用方保留“写入 save_path，返回远端标识”的包装契约；调度器可独立观察提交/查询/下载。异步协议不要求一次性改掉全部业务 HTTP 返回格式。
- 协议切换只影响新请求，在途 sync 先排空，不转换为另一份 async 作业。
- 异步端点缺失时报配置错误，不偷偷重发 sync。
- 提交超时、单次查询超时、生成总时限、下载超时、本地排队时限分开。POST 可能包含上传/预处理，不套用 3 秒探针预算。
- 保留全部参考媒体、task 和采样映射，改异步不能丢字段。vLLM-Omni 文件上传与 SGLang conditions 继续分别编码，不为统一调度强行统一请求体。
- 自定义同步驱动作为后续扩展，明确异常恢复能力较弱。

管理员纳管预检须列出未显式声明 video_api_mode、按默认值将使用 async 的 vLLM-Omni 模型，供启用实例前确认。协议控制与调度开关相互独立：设 video_api_mode=sync 不关闭调度，关闭 `.env` 的 `VC_VIDEO_DISPATCH__ENABLED` 也不恢复 sync。受管实例改 sync 必须先排空并退出池，之后也不能绕开仍存在的资源占位；恢复实例入池前重新验证 async 资格。不新增用于保存历史默认行为的兼容开关。调度开关由 `.env` 的 `VC_VIDEO_DISPATCH__ENABLED` 控制，改值需重建容器；协议字段仍在配置/API 内维护。

### 8.2 重试必须区分提交确定性

| 情况 | 处理 |
|---|---|
| 尚未提交：准备失败、确定连接建立前失败 | 结束 attempt；可恢复错误在原选定池重新排队或换等价成员，不跨池 |
| 驱动契约保证未受理的拒绝 | 退避重排，首期最多额外一次跨实例安全重试 |
| POST 读超时、途中断开、2xx 无合法 ID、不明确的 5xx | 标记 unknown，禁止自动换实例重发 |
| 已有远端 ID | 查询原实例原作业；查询失败不触发重新生成 |
| 完成后下载失败 | 重试下载，不重新生成 |
| 明确业务失败 | 透出；仅确定是提示词问题且计算已终止，允许 Doctor 新建尝试 |

接入时固定协议形态，受管调用不在不确定失败后轮流尝试多个创建变体。

本地幂等键可以防重复点击，不能凭空给予外部服务 exactly-once 能力。未返回 ID 的不确定提交默认需人工核对，不能仅因“现在指标为零”就自动重发。

## 9. 停止、恢复与配置变更

### 9.1 停止

- 排队中停止：原子撤销 queued/reserved，之后不能发送生成请求。
- 已提交停止：立即停止本次业务与后续排队项；只尝试取消本系统登记的作业，不取消外部作业。
- 取消不支持/未确认：保留资源占位，显示“本次任务已停止，服务端仍在收尾”。
- 用户可以立即重做，新执行排队或使用其他实例，但不能复用旧执行仍持有的槽。
- 迟到结果按 execution_id 防护，不覆盖新执行、不把停止阶段改为完成。

### 9.2 后端重启与故障

- 先恢复占位/尝试，再开放派发，不启动即清空槽。
- 旧执行未提交作业归 interrupted，沿用“用户确认重做”，不自动恢复业务生成。
- 有远端 ID 的在途尝试后台核对资源，必要时保留结果信息，不自动晋升旧执行产物。
- 无 ID、单查 404、观测失效进入待核对，不猜测终态或自动重发。
- 数据库不可用停止新派发，不回退内存锁继续提交。

### 9.3 热更新与维护

- 实例 draining 停止向该实例派发，在途继续核对；若池无其他可用成员，已入队批次按 §5.4 有限等待。
- 管理员下线整池（profile.enabled=false）是独立动作，二次确认后按 §5.4 以 pool_unavailable 提前结束未派发项，不等同于单实例维护。
- 在途作业存在时不得原地修改地址、resource_key 或凭据语义，先排空再改修订。
- 成员更新后，可用集合固定为“快照记录实例 ∩ 当前仍在该池且满足原契约、enabled/资格有效的实例”，去重后再做准入；新增成员不扩大已受理批次，移除成员不再接新片段。在途作业仍绑定原实例核对。
- profile 输出契约变更生成新 revision，旧版本不可静默改变。
- **关闭 `VC_VIDEO_DISPATCH__ENABLED`（`.env`）是运维级停用/回滚：只停止新的受管派发，不解除在途占位。** 改 env 需重建容器；这不是将所有入口自动改成 manual，受管 manual 也不能借此直连绕开调度。
- 关闭前二次确认并显示受影响的等待/在途数量。关闭生效后拒绝新受管作业；queued 和确定未发送的 reserved 作业以 dispatch_disabled 原因停止并结账，保留已完成产物，不再派发、不无限挂队。已提交或结果未知的尝试继续查询/下载/安全核对，槽位保持到确认结束。
- 存在本地发送线程或不确定提交时按在途处理，不能仅根据 reserved 名称认定未发送。停止未提交部分沿用执行级门控，迟到结果不能覆盖新执行。
- 再次开启不自动复活已停止批次，用户正常发起新执行即可；完全下线调度先完成在途核对。显式池外 manual 可用性另按其模型配置判定，不能据此承诺受管资源已释放。

## 10. 前端体验与管理员在线管理

### 10.1 普通用户

推荐文案：

- “视频生成：自动分配”。
- “已自动分配，正在生成第 2 个片段”。
- “等待视频生成资源，空闲后将自动开始”。
- “已完成 2 / 6，生成中 2，等待资源 2”。
- “已提交至共享服务，正在等待服务端处理”。
- “服务状态暂时无法确认，系统正在检查”。
- “资源池已开启但暂无就绪实例，可让管理员完成配置，或本次改用手动模型”。
- “未设置推荐池，已选择 X 池”（正常态，无显式偏好的新执行）。
- “默认池未就绪，已改用可用的 X 池”（确有推荐映射但未就绪）。
- “原自动分配池不可用，本次已改用 Y 池”（只对下一次新执行，不更改在途批次）。
- “资源池暂不可用，仍在等待原池恢复”（已入队后临时不可用）。
- “等待资源超时，已完成内容已保留”（queue_timeout，不是首次配置问题）。
- “资源池已下线，尚未开始的片段已结束等待”（pool_unavailable，在途继续安全收尾）。
- “资源池已由管理员停用，受管模型的新派发已暂停；可在高级入口选择可用的池外模型”（池外仍须合法性/映射检查，不是绕过槽位的通道）。

首页、顶栏、会话恢复三处都缺省 auto，auto 不保留具体模型 ID 默认值。正常显示“生成池”下拉和管理员推荐项，用户可以改选兼容池；具体模型下拉默认折叠，标题统一“高级：手动指定模型”。展开后显式选择/确认才使用 manual，收起/查看不自动改变模式。

就绪时显示“生成池：H3 首尾帧池 · SGLang；实例：自动分配”；未就绪显示缺项摘要与两个引导入口，不让 canStart 或缺少具体视频模型的校验把入口一起禁掉。配置补齐后保持 auto 的新执行直接走池，不要求再点一次模式开关。

manual 的用途与 §1.2 的定义一致，其他章节不另造例外；模型测试仍有真实调用确认。所有能映射到受管资源的调用继续共享同一占位和停用闸门。

引导提示按 `session_id + stage + client_submission_id` 去重（未建会话时用首页草稿标识）；前端每次明确提交生成一个 ID，重复点击的在途同次提交复用它。该 ID 只用于 UI/请求关联，不代替 owner 校验或后端幂等键。同一提交尝试的 HTTP/SSE/轮询事件只开一次弹窗；关闭后保留行内提示，自动轮询不重开。用户明确“重试”创建新提交尝试；配置变化先刷新缺项，只更新行内提示，不自动生成或重弹。上次 manual 选择最多作为本页建议值，不自动应用；切会话清除去重状态，刷新页面不因恢复状态自动弹窗。

多能力、多实例、公平轮转不存在稳定线性队列，不展示貌似精确的“第 N 位”。首期显示本人等待数、已等时长、所选池的匹配资源概况；未来有样本再给带置信区间的时间估计。

### 10.2 管理员界面

使用既有账号登录，在“设置 → 视频自动调度”管理：

1. profile：新增、复制、编辑名称/契约/成员，设置各生成方式默认档；契约变化生成新 revision。显式下线整池设置 enabled=false，二次确认展示等待/在途数量并按 §5.4 收尾；实例临时维护不自动触发整池下线。
2. 实例：选择既有视频模型或联动新增 provider/model，编辑资源键、专用/共享、探针地址/标签、启用/排空。
3. 查看只读探针、资格缺项；真实生成测试单列并提示消耗，不随保存触发。
4. 调整运行时 YAML 的等待时限、容量、推荐池和策略；常规默认模式固定 auto，manual 仅为显式高级操作，不提供“遇未就绪就把所有用户转手动”的选项。
5. 删除被默认配置、profile 或在途尝试引用的配置时拒绝并列依赖，先移除引用/排空；历史作业保留快照与审计，不级联删除。
6. 全局已开但资格/配置不齐时显示“已开启 / 未就绪（缺 N 项）”，逐项列出缺项和 §4.3 启用清单，不错误显示为已关闭。
7. 全局开关来自 `.env`，页面只读并标来源；关闭必须改 `.env` 后重建容器，说明等待作业停止、在途继续安全收尾且占位不释放。UI 使用真实 dispatch_enabled，不显示与后端开关相反的自动分配状态。
8. 纳管时列出使用默认 async 的模型及待确认协议，协议设置与调度停用独立，按 §8 管理。
9. 显示 `VC_VIDEO_PROFILES_FILE` 的来源与路径；池文件保存走独立写入口，不混入普通 `PUT /api/config`。

### 10.3 持久化与防覆盖

- `.env` 只管开关与路径：`VC_VIDEO_DISPATCH__ENABLED`、`VC_VIDEO_PROFILES_FILE`；被 env 覆盖时页面只读并标来源，保存不写回 env。
- 池与实例走独立 `GET/PUT /api/video/profiles`：读取运行时 YAML，保存时校验修订与引用，原子写文件（临时文件 + rename）并替换内存快照；过时编辑返回 409。
- 普通 `GET/PUT /api/config` 继续管理 providers/custom_models/models 等；其保存不得清空或回写池文件，旧设置页也不能覆盖池分区。
- 所有管理写入口服务端执行 require_admin，不仅隐藏按钮。
- 管理员身份来自 users.admin_logins / VC_USERS__ADMIN_LOGINS；不新建账号体系，不在样例中擅自授予管理员身份。
- 运行时 YAML 写锁与配置写锁分开；保存后新请求生效，无需重启后端；排队/运行项保留原契约，地址/资源/凭据变更按排空规则拒绝或保留草稿。
- 宿主直接改文件时按 mtime/摘要重载；解析失败保留上一份有效快照与 `configuration_errors`，不派发、不覆盖文件。
- `config.yaml` 的 config_revision、池文件的内容修订、profile.revision 是三个层次；池文件修订用内容摘要，避免手工编辑无法比对。
- 审计记录操作者、时间、非敏感差异，不记密钥明文。
- 排空、探针验证、异常核对使用独立管理员动作接口，不允许把运行态当普通配置任意写入。

### 10.4 查询接口与恢复

| 建议接口 | 用途 |
|---|---|
| GET /api/video/profiles?mode=... | 返回 dispatch_enabled、推荐池、每池 ready/not_ready/busy、公开缺项与适配性；未就绪不被静默过滤，GET 不触发探测 |
| PUT /api/video/profiles | 管理员保存运行时 YAML（池/实例/策略），校验 expected_revision 后原子写文件并热更新快照 |
| POST /api/video/profiles/reload | 宿主手工改文件后显式重载；解析失败保留上一份有效快照并返回缺项 |
| GET /api/video/resources/summary | 返回适当聚合、去敏的资源概况 |
| GET /api/video/jobs/{job_id} | owner/管理员读取作业 |
| 既有会话 /status 与 SSE | 增加 dispatch 摘要和排队/分配/远端等待事件 |
| 既有 stop 与独立任务取消入口 | 取消本次业务作业，校验归属 |

状态不能只存在于 SSE；刷新后从后端重查。排队子状态不替代既有完成度，versions/selected 仍按产物算。业务停止时资源收尾展示在独立摘要，不把片段重新标为 running。

沙盒提供显式异步选项，快速返回本地 job_id 后查询；同步响应入口内部也采用异步等待，不占共享阻塞线程。当前样例不提供 t2va 池时显式选择高级 manual，不将 pool_not_ready 自动转换为手动调用。Pipeline/工作流复用已有任务通道。

### 10.4.1 池查询响应字段

GET /api/video/profiles 接收生成方式及可选参数用于只读适配性检查；缺省不读取其他用户的会话。新执行实际解析还要带本用户显式偏好，不能把 GET 推荐结果当作入队凭据。

| 字段 | 类型与含义 |
|---|---|
| dispatch_enabled / config_revision | boolean / string；全局开关及配置版本 |
| configuration_errors | `{field, code, reason}[]`；手工配置造成的非法推荐引用等诊断，正常为 []；不以删除错误映射来冒充无推荐 |
| has_default_recommendation | boolean；当前方式是否存在有效非空管理员映射，不表示池已就绪 |
| default_profile_id | string 或 null；无映射时 null，不能编造推荐 |
| recommended_profile_id / recommendation_source | string 或 null / admin_default、fallback 或 null；当前只读建议，不回写会话 |
| recommendation_reason | none、no_default、default_not_ready、default_incompatible、no_ready_pool、no_compatible_pool；区分正常缺省与未就绪 |
| profiles[].id / revision / enabled | string / integer / boolean；池标识、契约版本、是否允许接单（配置缺省 true） |
| profiles[].state | ready、not_ready、busy；配置/资格/占用的摘要，按下述优先级生成 |
| profiles[].compatible / incompatibilities | boolean 或 null / 问题列表；未给足请求参数时 compatible=null，不谎称完成全部校验 |
| profiles[].ready_capacity / free_capacity | 非负整数；当前方式的合格去重资源槽数、通过 access_mode 分档准入且本地空闲的槽数；不能以 free_capacity 固化单执行并发 |
| profiles[].dispatchable | boolean；全局开、池开、请求兼容，至少一槽通过 §6.1 分档准入且空闲，并有全局名额时 true，仅是快照 |
| profiles[].missing / blocking_reasons | `{field, code, reason}[]` / `string[]`；前者配置/资格缺项，后者含 busy、probe_unknown、dispatch_disabled 等即时阻塞原因 |
| profiles[].observation | `{state, observed_at, expires_at, coverage, stale}`；state 为 idle、busy、unknown、unreachable、mixed，时间为 UTC ISO-8601 字符串或 null，coverage 为 complete、partial、none，stale 为 boolean |

聚合以当前方式的合格资源为范围，不对同一个 resource_key 重复计数：not_ready（池下线、契约缺项或该方式零合格容量）优先；否则所有匹配槽都被本地占位或可靠外部 busy 证实占用时为 busy，其余为 ready。**shared 的 ready + observation.unknown + dispatchable=false 是合法结果；正常 exclusive 可以 ready + observation.unknown + dispatchable=true**，空槽依据是独占账本。部分 busy、部分 shared unknown 时用 state=ready、observation.state=mixed 并标 probe_unknown；若还有正常 exclusive 空槽，可派发不能被 shared 的 unknown 一并阻塞。

observation.state 在各成员观测一致时取该值，不一致为 mixed；coverage=complete 仅在所有所需成员的观测均覆盖实际调用路径且新鲜时成立，有部分合格观测为 partial，全无为 none。时间使用参与聚合观测的最早 observed_at/expires_at，未观测为 null；任一必需观测缺失/过期则 stale=true。某成员 unknown 不阻止其他成员通过分档闸门；shared 的 unknown 不计为空闲，exclusive 只依核对后的独占账本计算空槽，不改变原始观测为 unknown 的事实。最终派发总要复查并原子占槽，GET 结果不是保证。

无 default_profiles 映射时 has_default_recommendation=false；有就绪兼容候选时 recommendation_reason=no_default，显示普通信息而非“默认池未就绪”。没有就绪池时 recommendation_reason=no_ready_pool，有就绪但无兼容项时为 no_compatible_pool，推荐 ID 均为 null；has_default_recommendation 仍独立如实返回。手工配置产生悬空非空 ID 时 configuration_errors 列出字段与原因，推荐 ID 为 null，不伪装成 no_default，也不静默 fallback；通过保存接口时应已拒绝该错误。

### 10.4.2 统一错误 detail 与会话状态

创建/阶段预检/介入入口共用 `VideoDispatchDetail` 结构；拒绝类错误返回 HTTP 409 的 `{detail: {...}}`，队列满为 429；已受理任务后续失败在任务查询及 SSE 的 error_detail 中使用同一内层结构，不可能追改已经返回的 HTTP 状态。

| 内层字段 | 类型与约定 |
|---|---|
| code | 固定 video_dispatch_error，供前端与 model_unavailable 区分 |
| error_code | pool_not_ready、pool_incompatible、selected_pool_not_ready、pool_unavailable、dispatch_disabled、queue_full、queue_timeout 等具体原因 |
| stage / mode / field | stage=video_generation；mode=auto 或 manual；field 为 video_profile_id、`VC_VIDEO_DISPATCH__ENABLED` 或具体参数字段 |
| profile_id / execution_id / submission_id | string 或 null；未受理时 execution_id=null，不制造运行执行；submission_id 仅关联提示去重 |
| reason / missing | 用户可读原因 / `{field, code, reason}[]`，无缺项则 [] |
| actions | 字符串数组；configure_pool、select_pool、edit_parameters、use_manual_once、retry 等，由前端受限映射为操作，不能是任意 URL |

例如零就绪的预检 detail：

```json
{"detail":{"code":"video_dispatch_error","error_code":"pool_not_ready","stage":"video_generation","mode":"auto","field":"video_profile_id","profile_id":null,"execution_id":null,"submission_id":"current-submission","reason":"资源池已开启但暂无就绪实例","missing":[{"field":"video_instances","code":"no_enabled_qualified_member","reason":"请完成实例配置及资格验证"}],"actions":["configure_pool","use_manual_once"]}}
```

- `_require_model_fields`、`_preflight_stage_models` 和工作流路由只包装同一 detail，不在某入口换成字符串。已有 manual 的 model_unavailable 与图片错误契约保持不变；auto 的本地资源错误不进入提示词 Doctor。
- lib/workflowApi.ts 对 video_dispatch_error 使用具名结构化异常并保留全部内层字段，WorkflowPanel 及 ModelFallbackDialog 按 mode/error_code/actions 渲染。busy/正常排队是进度不是异常，不弹“请更换视频模型”。
- 首次拒绝不创建视频运行执行、不改后端原阶段状态；前端撤销本次乐观 running，显示未就绪/参数引导，不改已经在运行的其他执行。/status 若无受理作业，dispatch.execution_id=null、phase=not_submitted；缺项由只读预检结果展示，不伪装成 waiting 作业。
- 正常整阶段已入队后阶段为 running，独立 dispatch.phase=queued；临时池不可用用 waiting_pool_unavailable；末端 phase=failed 时 error_detail.error_code 区分 queue_timeout/pool_unavailable。批次还有在途项时 phase=running，摘要保留 failed_count 和对应错误，待结账后依 §5.4 汇总为 failed/error。后台单条重生成不强行改变既有阶段状态，只增加执行归属下的 dispatch 摘要并沿用既有产物重算。阶段 waiting 仍表示等待用户确认，不能用于资源排队。
- dispatch 摘要携带 execution_id、profile_id、accepted_at、queue_deadline_at、queued_count、running_count、failed_count；拒绝时无计时起点，排队时用受理时间，不能把首次配置耗时加进等待时长。用户/运维停止仍按 stopped/interrupted，不新增 queue_timeout 等阶段枚举。

### 10.5 隔离要求

- owner 来自可信身份上下文，不采信请求体自报用户名。
- 普通用户看不到其他人的姓名、提示词、任务 ID、媒体 URL、实例地址或凭据；管理员可查看本系统占位归属。
- 外部任务只记录必要的计数/状态，不存其提示词、不假定能识别外部用户。
- 探针只访问管理员登记地址，不代理任意 URL，不跨源重定向携带凭据。
- `/api/config` 等已有出口也需检查，不能绕过新页面脱敏暴露实例私有信息。
- 忙闲探测与真实生成测试严格分开，后台不自动调用模型测试。

## 11. Pika-H3-Flex 与自定义 worker

README 和 Dockerfile 表明当前 Docker ENTRYPOINT 为 pika-h3-pro，是 CLI 打包，不是现成 HTTP 作业服务。一请求单 GPU，暴露八张 GPU 不会自动变成八并发。

建议后续在模型服务器提供轻量 worker 包装：

- 一个独立资源对应一个 worker/槽。
- 提供提交、查询、结果、健康/容量接口；只有确实能终止并确认结束才声明取消能力。
- 提交返回持久化 job_id，支持客户端幂等键；繁忙明确拒绝或使用有界队列，不隐藏长队列。
- VideoClaw 通过 HTTP 调用，不持有模型服务器 Docker socket，不执行任意远程 shell。
- 首期包装追求协议兼容；是否能常驻权重/缓存 adapter 单独验证，不承诺包装自动消除冷启动。
- Pika 使用独立 profile，按其 5–15 秒、480p/768p、FL2VA/Ref2VA 与媒体上限定契约。
- 六次 generator evaluations 不能直接套成现有 num_inference_steps=6 或 7，由独立驱动遵循原生采样契约。

本轮不修改 Pika 仓库、不构建镜像、不部署服务。

- **F8-0 单用户利用率**：一个 owner 六片段，三个合格独立实例、模型 concurrency 全为 1、策略≥3；经真实 VideoDirectorAgent.process 及介入重生成入口各验证首轮三个不同实例在途、其余三个等待。换双实例首轮两个；关闭并发首轮一个。初始槽全忙时入队、随后释放槽，验证不会永久卡在入队时的零空闲容量。此用例必须能在恢复原单模型线程池调用时失败。
- **F8-A 同池争用**：8 个可信测试 owner 同步屏障提交到同一个双实例池，每人 2 个片段；Fake 阻塞完成。确认 16 个唯一受理作业，稳定态两个远端在途、14 个本地等待，每 resource_key 最大在途=1；池表现为 busy 而不是 not_ready。不仅断言上限，也断言可用两槽确实被使用。
- **F8-B 四池混合**：8 个 owner 每池 2 人，每人 1 片段，模式匹配、8 个资源均就绪且空闲。首次派发收敛后恰好 8 个在途，每池 2 个、每资源 1 个；完成后 8 个结果与 owner/执行 ID 一一对应，无重复创建或串产物。另跑全首帧对照，仅两个 fl2va 池最多四槽，同池单执行最多两槽，不能错误期待八槽。
- **F8-C 未就绪对照**：8 个 owner 同时提交到零就绪环境；各收到结构化引导，新增调度作业=0、占位=0、模型 POST=0、占位地址探测=0，前端没有伪 running。
- **F8-D 等待中故障**：先入队再暂时停用全部匹配实例，记录 waiting_pool_unavailable，不改池、不重置期限；虚拟时间到原期限验证 queue_timeout。独立一轮管理员显式下线整池，在未达期限时验证未派发项 pool_unavailable、在途槽仍持有。
- **F8-E 公平与去重**：释放 Fake 完成屏障分轮观测，不把“总数相等”作为唯一证据；在八用户均有兼容等待项时每轮各派发一次，重复提交同幂等键不增作业。记录 resource 最大重叠、attempt/job/owner 映射、各轮派发顺序、零未就绪误判以及业务错误分类。

预期用例文件为 `backend/tests/test_video_dispatch_concurrency.py`，须随调度实现创建并真正接线；本轮不创建空测试或独立 Fake 调度器。不用宿主运行后端测试，不为此新建/重建镜像。

真实接入需另行授权，在服务可达时验收 idle→busy→idle、sync 覆盖、取消排空与作业查询。源码核实和 Mock 不能替代真机资格验证。

指标分别统计未就绪导致的配置阻塞次数/持续时间、本地队列等待、远端等待、推理、下载发布耗时，以及利用率、安全重试、未知作业、外部繁忙次数。未就绪尚未入队，不计入队列等待时长；模式停用也单独统计。需要对比时以显式 manual 实验建立基线，不改变产品默认，不预先承诺固定倍数提速。

## 14. 总结

资源池方向合适，但核心不是“自动找一个显示空闲的模型”，而是：

> **把相同生成能力的实例统一管理，让用户只表达需求，由后端公平排队、可靠占位、自动派发并解释等待。**

专用实例提供可靠主容量，共享实例提供有明确限制的补充容量；异步作业让调度可跟踪，管理员在线配置让日常增减实例不再依赖用户手工选模型。
