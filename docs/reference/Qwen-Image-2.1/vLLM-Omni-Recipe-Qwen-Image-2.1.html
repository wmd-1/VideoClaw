Qwen-Image-2.1

Text-to-image and image-conditioned generation with Qwen-Image 2.1

Saved locally from https://github.com/vllm-project/vllm-omni/blob/main/recipes/Qwen/Qwen-Image-2.1.md on 2026-11-06 (raw Markdown at https://raw.githubusercontent.com/vllm-project/vllm-omni/main/recipes/Qwen/Qwen-Image-2.1.md). This is the vLLM-Omni in-repo recipe, and it is the official deployment document for both checkpoints: Qwen/Qwen-Image-2.1 and the 8-step distilled Qwen/Qwen-Image-2.1-Turbo (its own section below). Upstream publishes no separate Turbo recipe; the vendor's own model cards live next to this file (Qwen-Image-2.1-Model-Card.md, Qwen-Image-2.1-Turbo-Model-Card.md). Everything after this note is the upstream file verbatim.

Summary

  • Vendor: Qwen
  • Model: Qwen/Qwen-Image-2.1, Qwen/Qwen-Image-2.1-Turbo (8-step distilled)
  • Task: Text-to-image generation and image-conditioned generation (editing)
  • Mode: Offline inference and online serving with optional step-wise execution
  • Maintainer: Community

Model id: Qwen/Qwen-Image-2.1 follows the reference diffusers documentation and may change before the official release — the final checkpoint name is subject to the official release.

When to use this recipe

Use this recipe as a starting point for running Qwen/Qwen-Image-2.1. A single pipeline class, QwenImage21Pipeline, handles both pure text-to-image requests (no condition image) and image-conditioned requests with up to 4 condition images: prompt and condition images are encoded together by a Qwen3-VL text encoder, so editing-style requests go through the same serving path as text-to-image.

Qwen-Image-2.1-Turbo (8-step distilled)

Qwen/Qwen-Image-2.1-Turbo is the 8-step distilled variant of Qwen-Image-2.1 and runs through the same QwenImage21Pipeline. Keep these differences from the base checkpoint in mind:

  • Do not pass num_inference_steps. The Turbo checkpoint's model_index.json ships a fixed sample_sigmas grid, which vLLM-Omni loads automatically. An explicit num_inference_steps is overridden by sample_sigmas, so omit it.
  • Do not enable CFG. As a distilled model it runs at CFG=1: leave true_cfg_scale at its default (1.0); setting true_cfg_scale > 1 (and a negative_prompt) is not meaningful for the distilled weights.
  • License: Qwen Research License (not Apache-2.0) — check the checkpoint card before commercial use.

Offline:

Online serving works the same as the base model (vllm serve Qwen/Qwen-Image-2.1-Turbo --omni --port 8091). The sampling grid can be overridden per request through the whitelisted sigmas extra-body parameter (both /v1/chat/completions and the multi-stage /v1/images/generations path). The default 8-step grid is [1.0, 0.978453, 0.95418, 0.926626, 0.89508, 0.845148, 0.704534, 0.414568]:

Four-GPU BF16 eager inference

Start a four-GPU server with the checkpoint's native eight-step schedule:

The default communication backend remains the reference all-to-all. On a qualified CUDA installation, opt into symmetric-memory exchange with --ulysses-a2a-permute. This requires a working CUDA compiler/toolkit and NCCL 2.28 or later with symmetric-memory device support, including the wheel library/header layout required by the current extension builder. Missing requirements fail explicitly at initialization when opted in. No rank-local fallback is attempted after collectives have started.

Eligible equal BF16 Q/K/V tensors then share one exchange; other layouts retain the separate exchanges. Backend selection uses the common parallel configuration; it does not depend on a model name or a hardware-name heuristic.

Shared kernels live under vllm_omni/diffusion/layers/: pointwise fusion preserves BF16 intermediate roundings. Both standalone RoPE and full head128 Q/K norm/RoPE require SM103 with CUDA/PyTorch 2.13, where the reduction and complex FMA order were validated. Other architectures, including SM90, retain the reference normalization and complex RoPE arithmetic. The channel-first VAE norm helper and epilogue are shared with Wan; Wan's channels-last policy stays in its own adapter.

Exact pure-T2I text conditioning is bounded by 16 entries and 16 MiB. Image conditioning, batched prompts, training/gradients, LoRA and CPU offload bypass and invalidate this cache. Geometry follows the request's KV lifetime, with weak ownership and denoise-finally cleanup that preserves decode graphs. Generated images and sampled latents are never reused by these optimizations.

After the server reports ready, send a full eight-step image request:

The response contains a base64-encoded PNG in data[0].b64_json. This request checks generation; it does not measure latency. For performance comparisons, freeze the benchmark and accuracy checks independently of the optimization, use identical inputs and declared configurations, and compare native RGB and alpha outputs. Report cold/unseen prompts separately from warmed repeated prompts, which can reuse exact text conditioning.

Online Serving

Start the server:

To enable the step-wise runtime:

Step execution batches compatible requests at the same KV-cache phase. The pipeline tags every request with a batch_compatibility_key (conditioning mode plus condition-image layout), so a newly arriving request that would otherwise join a batch already past its first denoising step is isolated by the scheduler and deferred until the in-flight batch drains — it no longer fails the whole batch. --max-num-seqs controls batch capacity.

CUDA Graph decode

Qwen-Image-2.1 automatically uses CUDA Graph for supported fixed-shape denoising decode steps when enable_cuda_graph_decode=True (the default) and enforce_eager=False. Prefill remains eager. This works with both request execution and --step-execution.

To disable graph capture while keeping the rest of the compilation setup:

The same control is available as Omni(..., enable_cuda_graph_decode=False) and as enable_cuda_graph_decode: false on a stage in the deployment YAML. --enforce-eager / enforce_eager: true remains the broader switch: it disables both graph capture and automatic torch.compile. The two optimizations stack: the DiT blocks are regionally torch.compile'd and graph capture records the compiled (fused) kernels, while inductor's own cudagraphs stay disabled so the two graph layers never nest. Measured on a single H200 (1024×1024, 50 steps, seed 42, BF16, true_cfg_scale=1.0, warmup 1 + median of 3): compile+graph 5.93 s, compile-only 6.88 s, graph-only 9.52 s, eager 8.28 s end-to-end per image; combo and compile-only vs eager are 38.10 dB PSNR (compile fusion drift), and graph-only vs eager is bit-identical.

The autoregressive engine's compilation_config.cudagraph_mode does not control this diffusion path; use enable_cuda_graph_decode (or enforce_eager for everything) to force eager decode execution.

TP/SP/ring parallelism, HSDP, cache hooks, quantized KV caches, dynamic LoRA, padded text masks, and a second in-flight request whose cache aliases an already-owned graph key fall back to eager decode. Model-level CPU offload does not disable decode graphs while enable_cuda_graph_decode stays on (the default). DiT weights stay on fixed device storage so captured pointers remain valid, and that storage is not released while the text encoder runs. Pass --no-enable-cuda-graph-decode (or enable_cuda_graph_decode: false) for the eager offload path, which moves DiT weights off the device and frees that VRAM. Peak memory for the default graph-plus-offload combination was not re-measured in this PR. Graphs keep separate entries for different image layouts and copy request-owned prefix K/V into static buffers before replay; each graph key has a single live owner at a time, so concurrent same-shape requests never overwrite each other's prefix. Those buffers require additional memory; graph entries are bounded by the transformer's cache limit.

Prefix KV cache

The transformer caches the text/condition-image prefix across denoising steps (a prefill/decode split keyed by CFG branch). The cache is enabled automatically when the checkpoint declares causal_condition: true and is re-created per generation, so no state leaks between requests. It changes the compute path — cached prefix vs. full recompute at every step — so exact numerical reproduction against a no-cache reference (e.g. the diffusers pipeline) requires matching the cache setting on both sides. The prefix KV cache is orthogonal to weight quantization and works unchanged under FP8.

FP8 quantization

Online FP8 quantization of the transformer is supported; the fused to_qkv projections load correctly, and the prefix KV cache path is unaffected. Only block-internal linears are eligible — the boundary projections (img_in/txt_in/modulation/proj_out/time_text_embed) stay in BF16 by construction:

ignored_layers entries are matched as name patterns for this model (e.g. img_mlp matches every block's img_mlp.proj/img_mlp.gate_layer/ img_mlp.out); exact full prefixes like transformer.transformer_blocks.3.attn.to_qkv also work.

A per-module sensitivity sweep (fixed prompt embeds / latent / timestep, 5 timesteps across the trajectory, relative L2 of the noise prediction vs BF16) ranks the groups: img_mlp is the most sensitive (3.8% max error on its own, driven by img_mlp.proj 2.8% and img_mlp.out 2.5%), then attn.to_out (2.7%), then attn.to_qkv (1.6%); errors are largest at the late (low-sigma) steps. End-to-end on H200, single GPU, same prompt as Quality Comparison ("A ceramic teapot on a wooden table", 1024×1024, 50 steps, seed 42, eager):

Quantization

Online FP8 is supported per component via quantization_config:

Either component can be quantized on its own. Measured on H200 at 1024×1024 (seed 42, 50 steps, same teapot prompt, eager): text-encoder FP8 lowers peak GPU memory from 36.9 GB (BF16) to 30.4 GB (−6.5 GB); T2I PSNR vs BF16 32.1 dB. DiT FP8-all is 30.4 GB / 6.06 s. Combined DiT+text-encoder FP8 was not re-measured on H200. The edit path routes condition images through the BF16 vision tower, so it is unaffected by text-encoder FP8. See docs/user_guide/quantization/fp8.md for the scope rules.

FP8 prefix KV storage

The cached prefix K/V can be stored in FP8 E4M3 (with per-token-per-head fp32 scales), halving the prefix-cache memory — relevant for long prompts (up to 8192 text tokens) and up to 4 condition images (~4096 latent tokens each). Prefill quantizes once; decode dequantizes per step, so attention compute is unchanged. Enable it through the model-specific extras config (e.g. in the deploy YAML's stage extras or as an Omni(...) engine kwarg):

Accepted values: "fp8" / "fp8_e4m3" (K and V quantized), "fp8_v" (V only — K stays in the native dtype), and None / "auto" (default, native dtype — behavior unchanged). This is independent of diffusion_kv_cache_dtype, which quantizes attention Q/K/V compute per forward pass on supported backends.

Measured on one NVIDIA H200, T2I 1024x1024 (seed 42, 50 steps, true CFG 4.0, eager, PSNR vs. the bf16 baseline on the same GPU): "fp8" 34.2 dB, "fp8_v" 44.0 dB. The error is dominated by K quantization: post-RoPE keys are the precision-sensitive half of the cache, so "fp8_v" buys back about 9.8 dB at 75% (instead of 50%) of the original cache size. The residual error is inherent e4m3 precision accumulated coherently over the denoising trajectory; finer scale granularity (per-tensor/per-head/per-token were compared) or Hadamard-rotated V did not improve it. The saving scales with prefix length. These sizes are calculated at the limit (8192 text tokens + 4 condition images, ~24.6k prefix tokens), not measured on the 1024 T2I run above: ~12.9 GB per CFG branch in bf16, ~6.6 GB in "fp8" and ~9.7 GB in "fp8_v". That is where this option matters. Treat it as an opt-in for memory-bound long-prompt / multi-image workloads, not a free lunch; "fp8_v" is the better default trade-off when quality matters.

Note: a quantized prefix cache is not CUDA-graph capturable — requests using this option stay on the eager decode path (a warning is logged once).

Why not the scheduler-managed paged KV (DiffusionKVCacheMode.PAGED_SCHEDULER)?

Evaluated and deliberately not adopted (see the qwen21-p0-kv commit message for the full analysis): the paged scheduler targets cross-request KV management — a statically sized page pool, block sharing/dedup, and eviction — whereas this prefix cache lives exactly as long as one generation and is sized once per request. Migrating would require routing decode attention through the worker paged adapter (writing fresh target K/V into pages every step), per-request page tables, and re-validating the block-causal piecewise-span masking and Ulysses/CFG constraints, for no memory benefit over the per-request dense tensors. The FP8 storage above captures the actual memory win at ~1% of the integration cost.

Known Limitations

  • Cache acceleration backends (cache_dit, tea_cache) are not supported; QwenImage21Pipeline is registered in _NO_CACHE_ACCELERATION.
  • Ulysses sequence parallelism is wired; ring attention is not a supported path. A short H200 smoke (1024×1024, 8 steps, seed 42, true CFG 1.0, eager) finished: Ulysses SP=2 vs SP=1 is 46.5 dB. That size's target length is divisible by 4, so SP padding was not exercised, and this is not the 50-step parity next to the TP tables. The features matrix therefore stays ❓. Ring SP=2 also ran, at 29.9 dB vs SP=1, which is why it stays unsupported.
  • Only true CFG is exposed; there is no guidance_scale knob.
  • VAE tiling (--vae-use-tiling, also implied by --vae-patch-parallel-size > 1) decodes in 512px tiles with 384px stride (32 latent pixels per tile at 16x spatial compression). On CUDA OOM the tile size is automatically halved (keeping 25% overlap) and decoding retried, down to 128px tiles. Tile sizes are not yet exposed as engine arguments.

NPU performance defaults

Qwen-Image-2.1 enables the following optimizations automatically on eligible NPU paths. The measured workload is Qwen-Image-2.1-Turbo, BF16, TP1, eager execution, batch 1, CFG1 and 1280×704 on Ascend 910B1. These defaults do not change the sampling schedule or select a different attention backend.

These optimizations are selected automatically, without environment switches:

  • Interleaved NPU RoPE.
  • Broadcast modulation during BF16 batch-1 eager decode without SP.
  • Residual buffer reuse during eligible BF16 eager inference.
  • NZ storage for eligible BF16 NPU linear weights.
  • Model-local fusion attention for eligible calls with SDPA selected.
  • Triton Ascend SwiGLU fusion on eligible Ascend910B1 BF16 inputs.

QWEN21_FUSION_PRECISE still controls fusion attention precision (default 0).

The automatic attention path requires TP1, no SP, no CPU offload, no quantization, batch 1, equal Q/K/V head counts, no metadata, no gradients and no compilation. It executes inside shared Attention dispatch. Other models, other selected backends, masked calls and graph execution keep their existing paths. Causal attention and unequal Q/K/V head counts also retain ordinary SDPA.

Automatic NZ conversion requires unquantized TP1 execution without CPU offload, sequence parallelism, HSDP or a configured lora_path, BF16 NPU weights, and allow_internal_format=True already configured in the runtime. Otherwise it is skipped. Eligibility follows eager execution, not enable_cuda_graph_decode. On NPU this transformer stays eager either way: Ascend does not torch.compile it, and CUDA graph capture does not run, so the default graph manager falls back to eager and still converts. The model never changes the global internal-format setting. Conversion is skipped when its prerequisites are absent. Conversion runs while the transformer loads its weights. Distilled LoRA fusion adds ND deltas into those weights afterwards, and HSDP shards or broadcasts them, so both configurations keep ND storage. Residual reuse requires the eager prepared-modulation path and does not mutate its input or combine multiplication/addition rounding into one fused operation.

VAE spatial-padding folding, prompt caching, request geometry reuse and shared modulation preparation apply under their own guards.

VAE normalization also reuses its fresh FP32 conversion buffer on NPU for FP16/BF16 inference without autograd or compilation. It preserves the L2 norm, epsilon clamp and sequential scaling operations, and never overwrites the input. A separate 1024×1024, 8-step Ascend 910B1 comparison validated pixel-identical outputs; its results should not be combined with the 1280×704 measurements above.

Unquantized NPU BF16 MLP inference also reuses fresh gate-projection storage for separate SiLU and multiplication operations. Autograd, compilation and other dtypes retain the original path. VAE normalization skips its fixed Python zero bias, while trainable tensor biases are still applied. These changes need no additional environment flags and were validated with the 1024×1024 workload.

Triton Ascend SwiGLU fusion

This path is enabled automatically when its eligibility checks pass. Earlier default-configuration measurements excluded this fusion and must not be treated as measurements of the new default. With Triton Ascend installed, unquantized eager BF16 inference on Ascend910B1 fuses the two-input SiLU/multiply path for batch 1, hidden width 4096 and sequence length at least 4096. Both projected tensors must have width 12288 and contiguous ND storage. Other cases use the existing implementation. The kernel reuses the fresh gate projection, preserves BF16 rounding after SiLU, and does not concatenate gate/up tensors. Sequence lengths share a single compiled kernel; initial compilation is excluded from warmed latency results.

Conditioning cache and graph fallback scope

The model-local text-only prompt cache matches upstream main. A single string prompt is cached directly and does not consult enable_prompt_embed_cache. Editing, multi-prompt calls, training, autograd, LoRA, and offload bypass the cache and drop stored text entries. The shared runner cache keeps its own default and collective-safety checks.

Single-request step decode retains its request KV owner. Geometry is stored per CFG branch on that owner; rebuilding an equivalent mask no longer invalidates it. Prefix layout must remain fixed for the lifetime of that branch's KV cache.

Shared modulation applies to eager prefill and eager decode fallback even when a decode graph manager exists. Captured graph execution is unchanged; no new graph-mode performance improvement is claimed.
